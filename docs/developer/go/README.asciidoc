=== PacketFence Golang libraries

==== Basic setup

This is a guide on how to setup/use the PacketFence Golang libraries.

To bootstrap the environment:

[source,bash]
----
cd /usr/local/pf/go
make go-env
----

To work directly on sources, run:

[source,bash]
----
cd go
GO_REPO=${PWD} make go-env
----

This will install Golang version use to build PacketFence Golang binaries and
check if all modules defined in [filename]`go.mod` are available.

Source the .bashrc to get the new environment variables:

[source,bash]
----
source ~/.bashrc
----

Get a complete overview of the Golang environment with [command]`go env` command.

==== Pulling the dependencies

Dependencies use go modules and will be fetched automatically during build time.

You will also need [package]`ipset-devel` and [package]`pkgconfig` libraries
which can be installed using the following command:

.RHEL-based systems
[source,bash]
----
yum install ipset-devel pkgconfig
----

.Debian-based systems
[source,bash]
----
apt install libipset-dev pkg-config
----

==== Update dependencies

After adding or removing Golang dependencies, run following command in [filename]`go` directory to update `go.mod` and `go.sum` files:

[source,bash]
----
go mod tidy
----

==== Building the code

All code should be built into a Caddy middleware which we'll then use in a
[filename]`Caddyfile` to create our recipes. Only reason for not using Caddy would be that
the binaries doesn't interact using HTTP (which Caddy can handle at some
point). For now, we'll focus only on services using HTTP until we're
confortable with Caddy.

A local version of Caddy is in [filename]`caddy/caddy`. This is a vendored version of Caddy which includes the plugins and middlewares for PacketFence.

In order to build the Caddy HTTP service (`pfhttpd`):

[source,bash]
----
make pfhttpd
----

Do the same to build `pfdns`, `pfdhcp`, `pfdetect` and `pfstats`:

[source,bash]
----
make all
make copy
----

==== Checks before building

Every binary target in [filename]`go/Makefile`, including race builds, depends on
[command]`make check`. The checks run once per make invocation, before any binary
is built, including when using [command]`make -j`. A failed gating check stops
the build, so there is no separate build step to run.
The PacketFence service Dockerfiles and Debian/RPM package builds already invoke
this Makefile, so they use the same gate.

Those package builds only run on `devel`, maintenance branches, tags and
manually triggered pipelines, so CI runs the gate itself on every push: the
`pre_ci_go_check_debian_bookworm` and `pre_ci_go_check_centos_8` jobs in the
`check` stage run [command]`make -C go check all` on each build image. Both are
needed because the gate uses the build host's OS.
Artifact jobs explicitly depend on both Go check jobs, so their `needs` lists
cannot bypass the Go gate when image builds are disabled.

To run the checks without building a binary, from the repository root:

[source,bash]
----
make -C go check
----

The gate runs, in order:

* `go vet ./...` for suspicious code and common mistakes. *Stops the build.*
* `staticcheck -tests -show-ignored ./...` for static analysis, including tests.
* `govulncheck ./...` for known vulnerabilities reachable from the code.
* `gosec ./...` for security issues in the source.

Only `go vet` stops the build today. The last three report their findings and
let the build continue, because the module currently carries a backlog they all
flag. Once a tool's findings are triaged, drop its leading `-` in
[filename]`go/Makefile` to make it gate as well.

Analyzer versions are pinned in [filename]`go/Makefile` and executed using
`go run package@version`. Go caches their downloads and compilation without
adding them to the application's [filename]`go.mod`. The first run needs network
access to fetch the tools; govulncheck also needs access to the vulnerability
database. While those three stay advisory, a tool that fails to download or run
is reported but does not fail the build.

Checks cover the entire module using the build host's OS and architecture with
cgo enabled. Install the native dependencies described above even when building
the static `pfconnector` binary. This is a host validation pass; it does not
validate code selected only by another OS, architecture, race tag, or custom
build flags passed through `ARGS`. Use `GOFLAGS` for build tags shared by checks
and compilation. The integration tests remain available through
[command]`make test`; they require a running test pfconfig process.

Review and fix reported findings; any analyzer suppression should be narrow and
explain why the finding is safe. No blanket exclusions are provided, including
for the vendored `chisel/` fork. `gopls check` is not needed in this gate: vet
and Staticcheck provide the batch analysis, while gopls remains useful in the
editor.

Docker can reuse a cached successful build layer, including its check results.
To refresh vulnerability results when sources have not changed, rebuild with
`docker build --no-cache` (or disable the Kaniko cache in CI). Tools run in the
builder stage and are not copied into the PacketFence runtime images. Builds of
external applications such as Semaphore and xcaddy do not use this Makefile.

==== Creating a service

Once `pfhttpd` is built, use a [filename]`Caddyfile` to load middleware and bind it on a specific port:

----
localhost:1234 {
  logger {
    requesthistory 100
    level DEBUG
  }
  statsd {
    proto udp
    prefix pfsso
  }
  pfsso
}
----

This file should be put in [filename]`/usr/local/pf/conf/caddy-services/pfexample.conf`

Note how the logger configuration can be controlled from the [filename]`Caddyfile`. If the middleware (in this example `pfsso`) uses or calls the logger, it *must* be declared in the [filename]`Caddyfile`.

If the middleware uses `statsd`, `statsd` does not have to be configured in the [filename]`Caddyfile` which will result in the packets just not being sent (a dummy `statsd` client will be created).

Start `pfhttpd` with the [filename]`Caddyfile` using the following command:

[source,bash]
----
/usr/local/pf/sbin/pfhttpd -conf
/usr/local/pf/conf/caddy-services/pfexample.conf
----

Once it is ascertained that the service is working correctly, create an instance of `pf::services::manager` for it. Also create a unitfile for it in [filename]`conf/systemd` like the following:

----
[Unit]
Description=PacketFence Example Service
Wants=packetfence-base.target packetfence-config.service
packetfence-iptables.service
After=packetfence-base.target packetfence-config.service
packetfence-iptables.service
Before=packetfence-pfexample.service

[Service]
PIDFile=/usr/local/pf/var/run/pfexample.pid
ExecStart=/usr/local/pf/sbin/pfhttpd -conf
/usr/local/pf/conf/caddy-services/pfexample.conf
Restart=on-failure
Slice=packetfence.slice

[Install]
WantedBy=packetfence.target
----

Make sure that the packaging is also updated to copy those files in the [filename]`/usr/lib/systemd/system` directory.

==== Running the tests

Like the <<_running_perl_unit_tests,perl unit tests>>, the Golang tests rely on the presence of the test `pfconfig` process to execute properly.

In order to start the test `pfconfig` process:

[source,bash]
----
cd /usr/local/pf/t && ./pfconfig-test
----

You can proceed to execute all or some of the Golang unit tests:

[source,bash]
----
cd /usr/local/pf/go
go test ./...

cd /usr/local/pf/go/firewallsso/lib
go test
----

To run all the tests easily, use:

[source,bash]
----
cd /usr/local/pf/go
make test
----
