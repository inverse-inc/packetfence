//== Admin UI plugins

A plugin adds a page to the admin UI without rebuilding it. The page is
described by a JSON *manifest* that the plugin serves over HTTP, and core
renders it with its own views and components. *A plugin never ships code to
the UI*: it can only use the templates, components and validators core
already provides, listed in
[filename]`html/pfappserver/root/src/plugins/catalog.json`.

This works the same on a systemd host and on Kubernetes: only the
PacketFence database (the `ui_plugin` table) and HTTP are involved.

<<_writing_a_plugin_from_scratch>> builds one from scratch, with a complete
service in Go ([filename]`docs/ui-plugins/examples/go-plugin`) and in Perl
([filename]`docs/ui-plugins/examples/perl-plugin`).

=== How it works

----
plugin service starts, serves <scheme>://<host>:<port>/manifest.json (https unless on the loopback)
  registers: its row of the ui_plugin table                (Go or Perl accessor)

admin logs in
  GET /api/v1/plugins               api-frontend, existing Go "api" handler
    reads the registrations         ui_plugin table, at most every 5s
    fetches each manifest           3s timeout, then refreshed in the background (30s, 5s for a failure)
    validates it against the catalog, leaves out (and logs) unreachable or invalid ones
  the UI adds the routes and sidebar items of each plugin

admin uses a plugin page
  * /api/v1/plugin/<name>/<path>    api-frontend, existing Go "api" handler
    checks the can of the manifest  (see ACL)
    proxies the declared API to <scheme>://<host>:<port>/<path>, JSON answers only

plugin service stops
  deregisters: the row is deleted                         (Go or Perl accessor)
----

A manifest is fetched once when its plugin is first listed. After that the
last result is answered at once and refreshed in the background, so a slow or
dead plugin does not slow down the admin UI. A plugin that stops without
deregistering (crash, killed pod) stays registered: it disappears from the UI
once a refresh of its manifest fails, within about 30s, and its pages answer
502 ("The plugin ... is unavailable") meanwhile. It is listed again as soon as
its manifest answers, or when it registers again.

The UI loads the plugins once per session, when the admin logs in or reloads
the page: their routes, menus and stores replace the ones of the previous
load. A manifest that changes after that (an `api.create` adds New and
Clone) needs a reload of the admin UI, or a new login, to show it. The routes
of a plugin that deregisters stay until then, they show the unavailable
view. If the list of the plugins cannot be loaded, the UI has none and tries
again at the next navigation.

The registrations are rows of the database: they survive a restart of any
service and every api-frontend reads the same ones, whatever the number of
pods.

`GET /api/v1/plugins` and `/api/v1/plugin/` are allowed to any admin by
api-aaa. What each admin sees and may call is decided by the `can` of the
manifest, see <<_ui_plugins_acl>>.

=== Registering a plugin

A plugin registers itself when its service serves its manifest, and
deregisters itself when it stops, with the PacketFence accessors in Go or in
Perl. Both write the same row and apply the same rules, so a plugin can use
either. They use the PacketFence database through the PacketFence
configuration: *the plugin never handles the database credentials*.

[options="header",cols="1,2,2"]
|===
|Operation |Go (`github.com/inverse-inc/packetfence/go/uiplugins`) |Perl (`pf::ui_plugins`)
|register or update itself |`uiplugins.Register(ctx, uiplugins.Registration{Name, Host, Port}) error` |`pf::ui_plugins::register({ name => ..., host => ..., port => ... })` returns `($status, $error)`
|deregister itself |`uiplugins.Deregister(ctx, name) error` |`pf::ui_plugins::deregister($name)` returns `($status, $error)`
|get one |`uiplugins.Get(ctx, name) (*Registration, error)`, nil when not registered |`pf::ui_plugins::get($name)` returns a hashref, undef when not registered
|list all |`uiplugins.List(ctx) (map[string]Registration, error)` |`pf::ui_plugins::list()` returns a hashref name to registration
|validate without writing |`Registration.Validate() error` |`pf::ui_plugins::validate($registration)` returns `($ok, $error)`
|===

[options="header",cols="1,4"]
|===
|Property |
|`name` |`^[a-z][a-z0-9_-]{0,62}$`, also the `id` of the manifest and the `<name>` of `/api/v1/plugin/<name>/`
|`host` |a hostname or an IP address *core* reaches the plugin service at (eg: its Kubernetes Service name, or `containers-gateway.internal`). Plain HTTP on the loopback only, HTTPS with a certificate valid for this host otherwise, see <<_the_api_of_a_plugin>>
|`port` |1 to 65535
|===

Register is an upsert: registering again updates the registration.
Deregistering a plugin that is not registered is not an error. The Go
functions `RegisterDB`, `DeregisterDB`, `GetDB` and `ListDB` do the same with
a `*sql.DB` of your own.

The table, for reference: `ui_plugin` (`name` primary key, `host`, `port`),
one row per plugin, kept until the plugin deregisters. A row is validated again
when it is read: one written by hand that breaks the rules above is logged and
left out.

Examples:

* Go: [filename]`docs/ui-plugins/examples/register.go`, registers, waits for
  SIGTERM or SIGINT, deregisters
* Perl: [filename]`docs/ui-plugins/examples/register.pl`
  `register <name> <host> <port>`, `deregister <name>`, `list`, eg for a
  systemd `ExecStartPost`/`ExecStopPost` or a Kubernetes `postStart`/`preStop`
  hook

=== The API of a plugin

The plugin serves its manifest at `/manifest.json` and the API of its page.
The admin UI reaches that API through api-frontend only:
`/api/v1/plugin/<name>/<path>` is passed to `<scheme>://<host>:<port>/<path>`,
with the query string and the body.

*Transport.* A plugin on the loopback of api-frontend (`127.0.0.0/8`,
`::1`, `localhost`: the same host or pod) is reached over plain HTTP. Any
other host is reached over *HTTPS*: its certificate must be valid for the
registered host and chain to the system authorities or to
[filename]`/usr/local/pf/conf/ssl/ui_plugins_ca.pem` (optional, PEM).
Redirects are not followed and the proxy settings of the environment are not
used. That file is read once, when api-frontend first contacts a plugin, and
the api-frontend log says whether it was loaded or is absent: after adding or
rotating it, restart api-frontend.

*What is passed.* Only the API methods the manifest declares: the path must
match one of its `api` paths (`{id}` is one segment, never empty, `.` or
`..` once decoded: an id the UI encoded may hold a `/`, the plugin gets it
encoded as the UI sent it, eg `items/site%2Fa`) with the verb of that method
(`list`/`item`: GET, `listOptions`/`itemOptions`: OPTIONS,
`search`/`create`: POST, `update`: PATCH, `delete`: DELETE). Anything else is
refused (403), and so is a call the admin is not allowed (see
<<_ui_plugins_acl>>).

* the admin token is not passed (`Authorization`, `Cookie` are removed), the
  plugin gets the admin api-aaa checked instead:
** `X-PacketFence-Username`
** `X-PacketFence-Admin-Roles`: the admin roles (eg: `ALL`)
** `X-PacketFence-Admin-Actions`: their actions on the targets the `can`s of
   the manifest name (eg: `SYSLOG_READ,SYSLOG_UPDATE` for a manifest about
   `syslog`)
+
No other `X-PacketFence-*` header reaches the plugin, whatever its spelling
(`_` for `-`, case).
* a request body is limited to 10 MB, a call to 60s

*What is answered.* The answer must be JSON (`application/json` or
`+json`, valid, at most 10 MB) or empty. It is passed with fixed headers
(`Content-Type: application/json`, `X-Content-Type-Options: nosniff`, a
sandboxing `Content-Security-Policy`, `Cache-Control: no-store`): the
headers of the plugin (cookies, CORS, ...) are not. A redirect, a 401 or 407,
anything else than JSON, a plugin whose manifest is unavailable or that does
not answer is a 502.

The answers follow the PacketFence API, as the core views expect them:
`{ "items": [...], "nextCursor": ... }` for a list or a search,
`{ "item": {...} }` for an item, `{ "meta": {...} }` for `OPTIONS`,
`{ "message": "..." }` for a write or an error. The UI shows the `message`,
`warnings[].message` and `errors[].message` of a plugin as text (escaped), and
ignores the `pattern`s of its `OPTIONS` meta (regular expressions the browser
would run): use a `matches` validator of the manifest instead.

=== Manifest

The manifest follows the JSON Schema
[filename]`docs/ui-plugins/manifest.schema.json` (generated from the
catalog). The API also checks that every validator applies to the type of its
component, that `when` names another field, and that the `api` paths have an
`{id}` where needed.

[options="header",cols="1,4"]
|===
|Property |
|`manifestVersion` |`1`
|`id` |the registered name
|`title`, `description` |translatable texts: `{ "en": "...", "fr": "..." }`, `en` is required
|`menu` |where the page goes, see below
|`template` |`resource` (one object, eg: a settings page) or `collection` (a list, and items to create, edit, clone, delete)
|`api` |the API of the page, see below
|`collection` |`collection` template only: `columns` (`key`, `label`, `sortable`) and `searchFields`
|`form` |`fields`, or `tabs` (`title`, `fields`)
|===

==== Menu

[options="header",cols="1,4"]
|===
|Property |
|`area` |`configuration`, `status`, `auditing`, `nodes`, `users` or `preferences`
|`section` |the path of an existing sidebar section, at any depth (eg: `/configuration/integration`). Without it the page is a new top-level section
|`group` |the untranslated name of a group of `section` (eg: `Main Configuration`)
|`before`, `after` |the path of a sibling item
|`icon` |a vue-awesome icon core already uses, for a new section
|`can` |*required*: the ACL needed to see the item, open the pages and call the plugin, see <<_ui_plugins_acl>>
|===

The page is at `/<area>/plugins/<id>` (and `/new`, `/<item id>`,
`/<item id>/clone` for a collection).

==== API

The same mapping as the `_api.js` of the core views: a path relative to the
plugin, `/api/v1/plugin/<name>/`, by method, called with a fixed verb. `{id}`
is the id of the item. A manifest cannot reach a core API.

[options="header"]
|===
|Method |Verb |`collection` |`resource`
|`list` |GET |path |
|`listOptions` |OPTIONS |path |
|`search` |POST |path |
|`create` |POST |path |
|`item` |GET |path with `{id}`, *required* |path, *required*
|`itemOptions` |OPTIONS |path with `{id}` |path
|`update` |PATCH |path with `{id}` |path
|`delete` |DELETE |path with `{id}` |
|===

`create`, `update` and `delete` are `{ "path": "...", "can": ... }`: the
`can` is required, the method is only offered to the admins it allows, and the
API refuses the call to the others (see <<_ui_plugins_acl>>). A path has one
`{id}` at most, and `search` cannot have the path of `create`.

A collection needs `list` or `search`. A missing method is not offered:
without `create` there is no "New" or "Clone", without `update` nothing can be
saved, without `delete` nothing can be deleted. The `OPTIONS` answers give the
form its meta (allowed values, placeholders, defaults, required fields) like
for the core views. The `OPTIONS` answers are the plugin's too: an empty
`{ "meta": {} }` is fine.

==== Form fields

[options="header",cols="1,4"]
|===
|Property |
|`namespace` |the property of the item, dots for nested ones (`a.b`); not `__proto__`, `constructor` or `prototype`
|`component` |a core component of the catalog, eg: `BaseFormGroupInput`, `BaseFormGroupChosenOne`, `BaseFormGroupSwitch`
|`label`, `text`, `placeholder` |translatable texts
|`props` |other properties of the component (eg: `options`, `enabledValue`). Not the ones set from the field properties or rendered as HTML (`forbiddenProps` of the catalog)
|`when` |show the field only when another one `equals`, `notEquals` or is `in` a list of values (one value at least); exactly one of the three
|`can` |show the field only to the admins allowed, see <<_ui_plugins_acl>>
|`validators` |`[{ "fn": "isPort" }, { "fn": "min", "args": [2], "message": { "en": "..." } }]`, the core validators of the catalog. A `matches` regular expression follows the rules below
|===

A tab (`tabs[]`) can also have a `can`: it is only shown to the admins
allowed.

==== `matches` regular expressions

The browser runs the regular expression (a JavaScript `RegExp` without
flags) on every keystroke, and the API checks it when it validates the
manifest. Only the syntax both read the same way is accepted:

* at most 256 characters
* escapes: `\d \D \w \W \s \S \b \B \n \r \t \f \v`, `\xHH` (two
  hexadecimal digits) and an escaped character that is not a letter or a digit
  (`\.`, `\-`, `\/`, `\]`...)
* groups: `(...)` and `(?:...)` only: no flags (`(?i)`), named groups
  (`(?P<id>...)`, `(?<id>...)`), lookarounds (`(?=...)`) or backreferences
  (`\1`)
* no POSIX classes (`[[:alpha:]]`, use `[a-zA-Z]`), no `\p{...}`, `\A`, `\z`,
  `\Q...\E` or `\x{...}`; a `]` first in a class is escaped (`[\]a]`)
* no nested quantifiers: a group repeated more than once (`*`, `+`, `{2,}`,
  `{1,3}`, `{3}`) cannot hold a quantifier (`*`, `+`, `?`, a variable
  `{m,n}`) or an alternation of more than single characters. The browser
  engine backtracks: `^(a|aa)+$`, `^((a+)b?)*$` or `^(\d+\.?)+$` freeze the
  page on a 30 characters input. A fixed count and an alternation of single
  characters are fine: `^(?:[a-f0-9]{2}:){5}[a-f0-9]{2}$`, `^(a|b)+$`.

A refused regular expression makes the whole manifest invalid: the plugin is
left out of the UI and the API logs the reason. Rewrite a nested pattern with
one level of repetition, or use a core validator:

[options="header"]
|===
|Refused |Instead
|`^(\d+\.?)+$` |`^[\d.]+$`
|`^(\w+-?)+$` |`^[\w-]+$`
|`^(?:[0-9]{1,3}\.){3}[0-9]{1,3}$` |the `isIpv4` validator
|`^(?=.*\d).+$` |`^.*\d.*$`
|`^(?i)[a-z]+$` |`^[a-zA-Z]+$`
|===

The texts of a manifest are shown as text: the markup of a `text` or a
validator `message` is escaped, a plugin cannot add HTML to the UI.

[[_ui_plugins_acl]]
==== ACL

A `can` is the JSON form of the `acl.$can`, `acl.$some` and `acl.$every` of
the core views, checked against the admin roles of the admin:

[options="header",cols="2,3"]
|===
|`can` |
|`"read syslog"` |`<verb> <target>`: the admin role `SYSLOG_READ`
|`{ "some": ["read syslog", "read system"] }` |any of them
|`{ "every": ["read syslog", "update syslog"] }` |all of them
|===

*Plugin actions.* Every plugin shares two admin actions:

[options="header",cols="1,1,3"]
|===
|Action |`can` |
|`PLUGIN_READ` |`read plugin` |reading the plugins
|`PLUGIN_WRITE` |`write plugin` |changing anything through a plugin. It is not allowed on a read-only cluster member
|===

They are in the role `ALL`, and can be given to any admin role. A plugin
uses them in its `can`s like any other action. They cover every plugin: an
admin with `PLUGIN_READ` can read all of them. A plugin that needs finer
rules checks `X-PacketFence-Username` and `X-PacketFence-Admin-Roles` itself.

`some` and `every` take `can`s, nested 3 levels at most. The verbs are the
actions of the admin roles (`read`, `create`, `update`, `delete`,
`create-multiple`, ..., `acl.verbs` of the catalog, `_` replaced by `-`), the
target is the rest of the role, lowercase (`CONFIGURATION_MAIN_READ` is
`read configuration_main`).

[options="header"]
|===
|Where |Without the ACL
|`menu.can` |no sidebar item, the routes of the plugin are refused (as the `meta.can` of a core route)
|`api.create.can` |no New and no Clone, the routes are refused
|`api.update.can` |no Save
|`api.delete.can` |no Delete
|a field or tab `can` |not shown
|===

The API checks the same `can`s for every call to the plugin: `menu.can` for
any request, and the `can` of `api.create`, `api.update` or `api.delete` for
those calls. `GET /api/v1/plugins` only lists the plugins whose `menu.can`
the admin satisfies. The `can` of a field or a tab only shapes the form: the
plugin checks its own rules with `X-PacketFence-Admin-Actions` if it needs to.

[[_ui_plugins_passthrough]]
=== Bundle plugins: the API passed through

A manifest with `"template": "bundle"` describes a page that is the plugin's
own code (no `api`, `collection` or `form`). Its API is *passed through*:

[source,json]
----
{
  "manifestVersion": 1,
  "id": "kit",
  "title": { "en": "Kit" },
  "menu": { "area": "status", "can": "read plugin" },
  "template": "bundle",
  "bundle": {
    "hostApi": 1,
    "mounts": ["page", "navbar-panel"],
    "navbar": { "icon": "toolbox" },
    "timeout": 120
  }
}
----

* any path under `/api/v1/plugin/<name>/` reaches the plugin, except a `.`
  or `..` segment
* the admin needs `menu.can`, and `PLUGIN_READ` for `GET` and `OPTIONS`,
  `PLUGIN_WRITE` for `POST`, `PUT`, `PATCH` and `DELETE`: the HTTP method
  decides, not the path
* any request body (eg: `multipart/form-data`), at most 10 MB
* a call may take `bundle.timeout` seconds (60 by default, 300 at most)
* a JSON answer is passed as JSON. Any other answer is passed with its media
  type as a download (`Content-Disposition: attachment`, with the filename
  of the plugin): it is never shown as a page of the PacketFence origin. The
  answer headers are fixed as for a manifest page (`nosniff`, a sandboxing
  `Content-Security-Policy`, `no-store`), a redirect or a 401/407 is a 502
* the plugin gets the same identity headers, never the admin token

*Read-only.* While the database is read-only (the `read_only` flag, or a
cluster member that is not ready), the writes to every plugin are refused
(403): the `POST`, `PUT`, `PATCH` and `DELETE` of a bundle plugin, and
`create`, `update` and `delete` of a manifest page. Reads still pass.

[[_ui_plugins_bundles]]
=== Bundle plugins: the code of the page

The page of a bundle plugin is a JavaScript module its *package* installs,
never the plugin service:

[options="header",cols="1,3"]
|===
|File |
|[filename]`/usr/local/pf/conf/plugins.d/<name>.js` |the module
|[filename]`/usr/local/pf/conf/plugins.d/<name>.conf` |its descriptor, with the SHA-256 of the module: `[bundle]` `sha256=<hex>`
|===

`GET /api/v1/plugins/<name>/bundle.js` serves the module to the admins who
satisfy `menu.can`, only when it matches the `sha256` of the descriptor. A
plugin service only registers a host and a port: it cannot give code to the
admin UI. The admin UI loads the module with the admin token, once per
session, and imports it.

*The module.*

[source,javascript]
----
export default {
  hostApi: 1,
  mount (el, host, { kind }) {
    const vm = new host.Vue({ render: h => h(Page, { props: { host, kind } }) }).$mount()
    el.appendChild(vm.$el)
    return () => vm.$destroy() // the unmount
  }
}
----

Build it as a library with `vue` external: use `host.Vue`, the Vue of the
admin UI, with its global components (BootstrapVue, `icon`).

*Mounts* (`bundle.mounts`):

[options="header",cols="1,3"]
|===
|Mount |
|`page` |the route `/<area>/plugins/<name>` and its sidebar item, from `menu`
|`navbar-panel` |a navbar button (`bundle.navbar.icon`, shown to the admins who satisfy `menu.can`) that opens a panel under the navbar. The panel is mounted when it is first opened and kept; one panel, or the documentation, is shown at a time
|===

*Host API, version 1* (`host`):

[options="header",cols="1,3"]
|===
|Property |
|`version`, `id` |`1`, the name of the plugin
|`Vue` |the Vue of the admin UI
|`api` |`request`, `get`, `options`, `post`, `put`, `patch`, `delete`: the API client of the admin UI, the paths relative to `/api/v1/plugin/<name>/`
|`can(can)` |the ACL of the admin, a manifest `can` (eg: `host.can('write plugin')`)
|`t(...)`, `locale()` |the translations and the language of the admin UI
|`navigate(to)` |a navigation of the admin UI
|===

[[_ui_plugins_database_tables]]
=== Database tables of a plugin

A package installed on top of PacketFence can add tables to the PacketFence
database. Its schema is kept the way PacketFence keeps its own
([filename]`db/pf-schema-X.Y.sql`, [filename]`db/upgrade-X.Y-X.Z.sql`), and
`pfcmd plugin schema` applies it.

*Descriptor.* The package installs [filename]`/usr/local/pf/conf/plugins.d/<name>.conf`:

[source,ini]
----
[plugin]
version=1.2
schema_dir=/usr/local/acme/db
----

*Files of `schema_dir`.*

[options="header",cols="1,3"]
|===
|File |
|`<name>-schema-X.Y.sql` |the whole schema of version X.Y, for a fresh install
|`upgrade-X.Y-X.Z.sql` |from version X.Y to X.Z. Starts with `CALL ValidatePluginVersion('<name>', X << 16 \| Y << 8);`
|`teardown.sql` |drops the tables, when the package is purged
|===

Each schema and upgrade file ends by recording its version, like the
PacketFence files do in `pf_version`:

[source,sql]
----
INSERT IGNORE INTO plugin_version (name, id, version, created_at) VALUES ('acme', @VERSION_INT, CONCAT_WS('.', @MAJOR_VERSION, @MINOR_VERSION), NOW());
----

Every file must be safe to run again after a failure: `CREATE TABLE IF NOT
EXISTS`, and the helpers of [filename]`db/upgrade-helpers.sql`
(`AddColumnUnlessExists`, `DropColumnIfExists`, `AddIndexUnlessExists`,
`DropIndexIfExists`, `CopyRowsInBatches`, `ValidatePluginVersion`) instead
of the `IF [NOT] EXISTS` clauses of `ALTER TABLE`, which MySQL does not have.
They are loaded before each file, in the same session, and dropped after it.
Do not add foreign keys to the PacketFence tables: they would block the
upgrades of PacketFence. [filename]`t/data/ui_plugins/acme` is a complete
example.

*Commands.*

[options="header",cols="2,3"]
|===
|Command |
|`pfcmd plugin schema apply <name> [--defaults-file=<file>]` |runs the schema file (fresh install) or the upgrade files up to the version of the descriptor, as the MariaDB root user through the local socket, or with a mysql client options file. Exits 2 when it cannot connect, with the command to run by hand. Call it from the package postinst / `%post`
|`pfcmd plugin schema check <name>` |exits 0 when the tables are at the version of the descriptor; it only reads the database. Call it before the service of the package starts
|`pfcmd plugin schema drop <name> [--defaults-file=<file>] [--force]` |runs `teardown.sql` and forgets the package. Call it when the package is purged: `apply` keeps a copy of `teardown.sql` in [filename]`/usr/local/pf/var/plugins/<name>/`. On a cluster member it refuses without `--force`: every node shares the tables
|===

On a cluster every node runs `apply`: the first one changes the tables, the
others find them at the version already. The database is never downgraded:
`check` fails when it is newer than the package.

*Changing a large table.* An `ALTER TABLE` of a large table locks it, and on
a Galera cluster blocks every node while it runs. Rebuild it instead
([filename]`t/data/ui_plugins/acme/upgrade-1.1-1.2.sql`):

. drop the leftovers of a failed run: `DROP TABLE IF EXISTS t_new`, `t_old`
. `CREATE TABLE t_new LIKE t`, then drop its secondary indexes
  (`DropIndexIfExists`): the copy keeps its primary key only, Galera needs it
. change the schema of `t_new` only
. copy the rows: `CALL CopyRowsInBatches('t', 't_new', '<columns>', '<integer key>', 10000)`,
  one transaction per batch
. add the indexes to `t_new` (`AddIndexUnlessExists`)
. `RENAME TABLE t TO t_old, t_new TO t`: one statement, `t` always exists
. `DROP TABLE t_old`

The rows written during the copy are lost: stop the service of the package on
every node before upgrading a package that rebuilds a table. Foreign keys
follow a renamed table: drop and add them around the rename.

=== Examples

* [filename]`docs/ui-plugins/examples/go-plugin` and
  [filename]`docs/ui-plugins/examples/perl-plugin`: complete plugin services
  that register themselves, the scaffolds of <<_writing_a_plugin_from_scratch>>

[filename]`docs/ui-plugins/examples/server.py` is an example plugin service,
Python standard library only: it serves the manifest of a directory and the
API of its page from memory (and `meta.json`, `data.json` when present).

* [filename]`docs/ui-plugins/examples/hello`: a collection, with `can`s on
  the menu, the write methods and a field, `when`, validators and `OPTIONS`
  meta
* [filename]`docs/ui-plugins/examples/hello-settings`: a resource with tabs

To try one on the host of api-frontend (loopback, plain HTTP):

[source,bash]
----
docs/ui-plugins/examples/server.py docs/ui-plugins/examples/hello --host 127.0.0.1 --port 8090 &
docs/ui-plugins/examples/register.pl register hello 127.0.0.1 8090
----

From another host, serve HTTPS with a certificate valid for the registered
host (`--tls-cert`, `--tls-key`). Run `register.pl deregister hello` when you
stop it.

=== Catalog

[filename]`html/pfappserver/root/src/plugins/catalog.json` is the only list of
what a manifest may use. After changing it:

[source,bash]
----
node html/pfappserver/root/build/ui-plugins-catalog.js
----

regenerates [filename]`go/uiplugins/catalog.json` (embedded in the API) and
[filename]`docs/ui-plugins/manifest.schema.json`, and checks that
[filename]`src/plugins/registry.js` has a loader for every component and a
builder for every validator. Every component of the catalog is referenced by a
lazy loader in the registry, so it is always in the build, even if no core
view used it anymore (today they all are in the initial `app` chunk already,
through the core views).

[[_writing_a_plugin_from_scratch]]
=== Writing a plugin from scratch

This section builds a plugin service step by step, with a complete example in
each language:

* Go: [filename]`docs/ui-plugins/examples/go-plugin` (`main.go`, `manifest.json`)
* Perl: [filename]`docs/ui-plugins/examples/perl-plugin` (`plugin.pl`, `manifest.json`)

Both serve the same page, a collection of notes kept in memory, and both were
run against the PacketFence API: list, search, paging, create, update and
delete, registration at startup, deregistration on SIGTERM. Copy one and
rename it.

==== What a plugin is

A plugin is an HTTP service of your own, with three parts:

[options="header",cols="1,4"]
|===
|Part |What it does
|`manifest.json` |describes the page: where it goes in the menu, the ACL, the API paths, the form. Only the core components and validators can be used, no code reaches the UI
|the API of the page |the paths the manifest names, answering JSON in the format of the PacketFence API
|the registration |tells PacketFence the name, host and port of the service when it starts, removes it when it stops
|===

PacketFence fetches the manifest, adds the page to the admin UI, and passes
the calls of the page to the service through `/api/v1/plugin/<name>/<path>`,
after checking the admin and the ACL of the manifest.

==== Checklist

. Pick a *name*: `^[a-z][a-z0-9_-]{0,62}$`, it is the `id` of the manifest,
  the URL segment `/api/v1/plugin/<name>/` and the key of the registration.
. Pick the *admin roles* the page needs, among the existing ones (a plugin
  cannot add roles): a target and its actions, eg `SYSLOG_READ`,
  `SYSLOG_CREATE`, `SYSLOG_UPDATE`, `SYSLOG_DELETE` are written
  `read syslog`, `create syslog`, ... in the manifest. The actions
  `PLUGIN_READ` and `PLUGIN_WRITE` (`read plugin`, `write plugin`) exist for
  the plugins themselves, see <<_ui_plugins_acl>>.
. Write the *manifest*, and check it against
  [filename]`docs/ui-plugins/manifest.schema.json`.
. Write the *API*: one route per method of the manifest.
. Decide *where it runs* and how PacketFence reaches it: plain HTTP on the
  loopback of api-frontend only, HTTPS with a trusted certificate otherwise.
. *Register* at startup, *deregister* on SIGTERM, with the Go or Perl
  accessors. The service never handles the database credentials.
. Run it as a *service* (systemd unit, Kubernetes deployment).
. *Test* it through the PacketFence API.

==== Layout

----
notes-go/                         notes-perl/
├── go.mod                        ├── manifest.json
├── main.go                       ├── plugin.pl
├── manifest.json (embedded)      └── notes-perl.service
└── notes-go.service
----

==== The manifest

The manifest of the examples ([filename]`docs/ui-plugins/examples/go-plugin/manifest.json`):

[source,json]
----
{
  "manifestVersion": 1,
  "id": "notes-go",
  "title": { "en": "Notes (go plugin)", "fr": "Notes (plugin go)" },
  "menu": { "area": "configuration", "section": "/configuration/integration", "can": "read syslog" },
  "template": "collection",
  "api": {
    "list": "notes",
    "listOptions": "notes",
    "search": "notes/search",
    "create": { "path": "notes", "can": "create syslog" },
    "item": "notes/{id}",
    "itemOptions": "notes/{id}",
    "update": { "path": "notes/{id}", "can": "update syslog" },
    "delete": { "path": "notes/{id}", "can": "delete syslog" }
  },
  "collection": {
    "columns": [ { "key": "id", "label": { "en": "Name" }, "sortable": true }, { "key": "text", "label": { "en": "Text" } } ],
    "searchFields": ["id", "text"]
  },
  "form": {
    "fields": [
      { "namespace": "id", "component": "BaseFormGroupInput", "label": { "en": "Name" },
        "validators": [ { "fn": "required" }, { "fn": "matches", "args": ["^[a-z0-9-]+$"] } ] },
      { "namespace": "text", "component": "BaseFormGroupTextarea", "label": { "en": "Text" },
        "validators": [ { "fn": "required" } ] }
    ]
  }
}
----

The rules that are easy to miss:

* `menu.can` is *required*, and so is the `can` of `create`, `update` and
  `delete`: the API checks them on every call to the plugin.
* `id` equals the registered name.
* An API path is relative to the plugin, has one `{id}` at most, and
  `search` cannot have the path of `create`.
* `template: "resource"` is one object (a settings page): `item` (GET),
  `itemOptions`, `update`; the paths have no `{id}`.

Check it before running anything, with any JSON Schema 2020-12 validator, eg:

[source,bash]
----
npm i ajv@8
node -e '
const Ajv = require("ajv/dist/2020").default, fs = require("fs")
const v = new Ajv({ strict: false }).compile(JSON.parse(fs.readFileSync("docs/ui-plugins/manifest.schema.json")))
console.log(v(JSON.parse(fs.readFileSync("manifest.json"))) || v.errors)'
----

The API applies a few more checks (validator types, `when` fields): a
manifest it refuses is logged by api-frontend, see
<<_ui_plugins_troubleshooting>>.

==== The API contract

[options="header",cols="1,2,2"]
|===
|Method of the manifest |Request |Answer
|`list` |`GET /notes?cursor=&limit=&sort=&fields=` |`{ "items": [...], "nextCursor": n, "prevCursor": n, "total_count": n }`, no `nextCursor` on the last page
|`search` |`POST /notes/search`, `{ "query": {...}, "cursor": n, "limit": n, "sort": [...], "fields": [...] }` |like `list`
|`listOptions`, `itemOptions` |`OPTIONS /notes`, `OPTIONS /notes/<id>` |`{ "meta": { "<field>": { "allowed": [{ "value", "text" }], "default": ... } } }`, `{ "meta": {} }` is fine
|`item` |`GET /notes/<id>` |`{ "item": {...} }`, 404 when it does not exist
|`create` |`POST /notes`, the item |201 `{ "id": "...", "message": "..." }`, 409 when it exists
|`update` |`PATCH /notes/<id>`, the item |200 `{ "message": "..." }`
|`delete` |`DELETE /notes/<id>` |200 `{ "message": "..." }`
|errors | |`{ "message": "...", "errors": [{ "field": "<namespace>", "message": "..." }] }` with 4xx: the field errors show under the form fields
|===

What PacketFence guarantees and expects:

* *Only these calls reach the service.* The path and verb must be a method
  of the manifest, and the admin must satisfy `menu.can` and the `can` of
  the method. The service still validates its input.
* *The admin, not their token.* Use these headers, never anything from the
  client:
** `X-PacketFence-Username`: the admin
** `X-PacketFence-Admin-Roles`: their admin roles (eg `ALL`)
** `X-PacketFence-Admin-Actions`: their actions on the targets the manifest
   names (eg `SYSLOG_READ,SYSLOG_UPDATE`); check the `can` of a field or a tab
   here, the UI only hides them
* *JSON only.* Any other answer, a redirect, a 401/407 or more than 10 MB
  is turned into a 502. Your headers (cookies, CORS, ...) are not passed.
* *Texts are text.* `message`, `errors` and `warnings` are shown escaped:
  HTML in them is displayed, not rendered.

==== Go

Full code: [filename]`docs/ui-plugins/examples/go-plugin/main.go`.

*Module.* The accessors are in `github.com/inverse-inc/packetfence/go/uiplugins`.

* In the PacketFence tree, put the plugin under [filename]`go/cmd/<name>/` and
  it builds with the PacketFence module.
* In a repository of its own:
+
----
module example.com/notes-go

go 1.26.4

require github.com/inverse-inc/packetfence/go v0.0.0
replace github.com/inverse-inc/packetfence/go => /path/to/packetfence/go
----
+
or a `go.work` with `use ( . /path/to/packetfence/go )`.

*The skeleton:*

[source,go]
----
//go:embed manifest.json
var manifest []byte

func routes() *http.ServeMux {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /manifest.json", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		w.Write(manifest)
	})
	mux.HandleFunc("GET /notes", list)          // list
	mux.HandleFunc("POST /notes/search", search) // search
	mux.HandleFunc("POST /notes", create)       // create
	mux.HandleFunc("GET /notes/{id}", item)     // item
	mux.HandleFunc("PATCH /notes/{id}", update) // update
	mux.HandleFunc("DELETE /notes/{id}", remove) // delete
	mux.HandleFunc("OPTIONS /notes", options)    // listOptions
	mux.HandleFunc("OPTIONS /notes/{id}", options) // itemOptions
	return mux
}

func main() {
	listener, _ := net.Listen("tcp", "127.0.0.1:8092")
	server := &http.Server{Handler: routes()}
	go server.Serve(listener) // or ServeTLS, see "Where it runs, and HTTPS"

	// register once the service answers
	r := uiplugins.Registration{Name: "notes-go", Host: "127.0.0.1", Port: 8092}
	if err := uiplugins.Register(ctx, r); err != nil {
		log.Fatal(err)
	}

	stop := make(chan os.Signal, 1)
	signal.Notify(stop, syscall.SIGTERM, syscall.SIGINT)
	<-stop
	uiplugins.Deregister(ctx, r.Name)
	server.Shutdown(ctx)
}
----

*Build and run:*

[source,bash]
----
go build -o notes-go .
./notes-go -listen 127.0.0.1:8092
./notes-go -listen 0.0.0.0:8443 -host containers-gateway.internal -port 8443 -tls-cert notes.crt -tls-key notes.key
----

`uiplugins.Register` reads the database settings from pfconfig, like the other
PacketFence Go services: `PFCONFIG_PROTO`, `PFCONFIG_TCP_HOST` and
`PFCONFIG_TCP_PORT` in the environment, and `PF_SYSTEM_INIT_KEY` or
[filename]`conf/system_init_key`. `-register=false` starts the service without
registering, for a registration done by `register.pl`.

==== Perl

Full code: [filename]`docs/ui-plugins/examples/perl-plugin/plugin.pl`.

*Dependencies.* The plugin runs with the Perl of PacketFence, which ships
Mojolicious, on a host or in a container that has the PacketFence tree
([filename]`/usr/local/pf/lib`, [filename]`/usr/local/pf/lib_perl`) and
reaches pfconfig.

*The skeleton:*

[source,perl]
----
use lib qw(/usr/local/pf/lib /usr/local/pf/lib_perl/lib/perl5);
use Mojolicious::Lite;
use Mojo::Server::Daemon;
use pf::error qw(is_error);
use pf::ui_plugins;

get '/manifest.json' => sub { my ($c) = @_; $c->res->headers->content_type('application/json'); $c->render(data => $manifest) };
get     '/notes'        => \&list;     # list
post    '/notes/search' => \&search;   # search
post    '/notes'        => \&create;   # create
get     '/notes/:id'    => \&item;     # item
patch   '/notes/:id'    => \&update;   # update
del     '/notes/:id'    => \&remove;   # delete
options '/notes'        => sub { $_[0]->render(json => { meta => {} }) };

my $daemon = Mojo::Server::Daemon->new(app => app, listen => ['http://127.0.0.1:8093']);
$daemon->start;

# register once the service answers
my %registration = (name => 'notes-perl', host => '127.0.0.1', port => 8093);
my ($status, $error) = pf::ui_plugins::register(\%registration);
die "$error\n" if is_error($status);

my $stop = sub { pf::ui_plugins::deregister('notes-perl'); Mojo::IOLoop->stop };
local $SIG{TERM} = $stop;
local $SIG{INT}  = $stop;
Mojo::IOLoop->recurring(1 => sub { }); # let Perl deliver the signals
Mojo::IOLoop->start;
----

*Run:*

[source,bash]
----
/usr/local/pf/docs/ui-plugins/examples/perl-plugin/plugin.pl --listen http://127.0.0.1:8093
plugin.pl --listen 'https://0.0.0.0:8443?cert=notes.crt&key=notes.key' --host containers-gateway.internal --port 8443
----

`--no-register` starts the service without registering.

==== Where it runs, and HTTPS

PacketFence reaches a plugin over plain HTTP *only on the loopback of
api-frontend* (`127.0.0.0/8`, `::1`, `localhost`). Anywhere else it uses
HTTPS and verifies the certificate.

[options="header"]
|===
|Deployment |Host to register |Transport
|Kubernetes, the plugin is a container of the api-frontend pod |`127.0.0.1` |HTTP
|Kubernetes, the plugin has its own Service |the Service name, eg `notes-go.packetfence.svc` |HTTPS, certificate for that name
|systemd host: api-frontend runs in a container, the plugin on the host |`containers-gateway.internal` (the host, as the containers see it) |HTTPS, certificate for `containers-gateway.internal`
|another server |its name |HTTPS, certificate for that name
|===

On a systemd host the plugin must listen on an address the containers reach,
eg `0.0.0.0:8443` with the port open to the container network only.

The certificate must chain to a system authority, or to the authorities in
[filename]`/usr/local/pf/conf/ssl/ui_plugins_ca.pem` (PEM, optional, read by
api-frontend). A CA of your own, eg:

[source,bash]
----
# once: a CA for the plugins, trusted by api-frontend
openssl req -x509 -newkey rsa:3072 -nodes -days 3650 -subj "/CN=PacketFence UI plugins CA" \
  -keyout ui_plugins_ca.key -out /usr/local/pf/conf/ssl/ui_plugins_ca.pem

# per plugin: a certificate for the host PacketFence reaches it at
openssl req -newkey rsa:3072 -nodes -subj "/CN=containers-gateway.internal" -keyout notes.key -out notes.csr
openssl x509 -req -in notes.csr -CA /usr/local/pf/conf/ssl/ui_plugins_ca.pem -CAkey ui_plugins_ca.key \
  -CAcreateserial -days 825 -out notes.crt \
  -extfile <(printf "subjectAltName=DNS:containers-gateway.internal\nextendedKeyUsage=serverAuth")
----

Keep the CA key off the PacketFence server, and restart api-frontend after
changing `ui_plugins_ca.pem`.

==== Running it as a service

*systemd*, eg [filename]`/etc/systemd/system/notes-go.service`:

[source,ini]
----
[Unit]
Description=PacketFence admin UI plugin notes-go
After=packetfence-pfconfig.service packetfence-api-frontend.service
Wants=packetfence-pfconfig.service

[Service]
ExecStart=/usr/local/pf/plugins/notes-go/notes-go -listen 0.0.0.0:8443 -host containers-gateway.internal -port 8443 -tls-cert /usr/local/pf/plugins/notes-go/notes.crt -tls-key /usr/local/pf/plugins/notes-go/notes.key
# SIGTERM: the plugin deregisters itself
KillSignal=SIGTERM
TimeoutStopSec=15
Restart=on-failure

[Install]
WantedBy=multi-user.target
----

For the Perl plugin, `ExecStart=/usr/local/pf/plugins/notes-perl/plugin.pl
--listen 'https://0.0.0.0:8444?cert=...&key=...' --host containers-gateway.internal --port 8444`.

*Kubernetes:* run the plugin as a container of the api-frontend pod
(loopback, plain HTTP), or as a Deployment with a Service and a certificate
for the Service name. The container needs what the accessors use: pfconfig
(`PFCONFIG_TCP_HOST`, `PFCONFIG_TCP_PORT`) and the system init key for Go, the
PacketFence tree for Perl. Give the pod a `terminationGracePeriodSeconds` long
enough to deregister. A plugin killed without deregistering stays registered:
its pages answer 502 and it drops out of the menus within about 30s.

==== Testing it

With an admin token (`POST /api/v1/login`):

[source,bash]
----
TOKEN=...
API=https://<packetfence>:1443/api/v1
curl -sk -H "Authorization: Bearer $TOKEN" $API/plugins | jq '[.items[].id]'
curl -sk -H "Authorization: Bearer $TOKEN" $API/plugin/notes-go/notes
curl -sk -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -X POST $API/plugin/notes-go/notes -d '{"id":"first","text":"hello"}'
----

Then open Configuration -> Integration -> "Notes (go plugin)" in the admin UI.
`register.pl list` shows the registrations.

[[_ui_plugins_troubleshooting]]
==== Troubleshooting

[options="header",cols="2,3"]
|===
|Symptom |Where to look
|The plugin is not in `GET /api/v1/plugins` |api-frontend logs `UI plugin "<name>" ignored: ...` with the reason (manifest refused, fetch failed, certificate not trusted). An admin without the `menu.can` does not get it either
|403 `... is not an API method of the manifest` |the path or the verb is not a method of the manifest (eg `PUT` instead of `PATCH`, a path with two segments for `{id}`)
|403 `... do not satisfy ...can` |the admin lacks the roles of the `can`
|502 `The plugin "<name>" is unavailable` |the service does not answer, its certificate is not trusted, or it answered something else than JSON, a redirect, a 401/407, or more than 10 MB (api-frontend logs which)
|The page shows but a field is missing |the `can` of the field or its tab, or its `when`
|===
