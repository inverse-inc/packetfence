[[aruba-cx-switch-limitations]]
=== Aruba CX switches authenticate but CoA/SNMP fail

*Problem:* CX switches successfully authenticate users but Change of^[1]^
Authorization (CoA) and SNMP functions don't work properly.

*Symptoms:*

[options="compact"]
 * Initial 802.1X authentication succeeds
 * User gets network access with initial role/VLAN
 * Role changes in PacketFence don't reflect on switch ports
 * SNMP queries to switches timeout or fail
 * Port status changes don't trigger in PacketFence
 * Manual disconnection/reconnection required for role changes
 * PacketFence logs show CoA failures or timeouts

*Solution:*

*This is a known limitation with CX switches:*

*What Works:*
[options="compact"]
 * Initial 802.1X authentication
 * User role assignment
 * Basic RADIUS communication

*What Doesn't Work:*
[options="compact"]
 * CoA (Change of Authorization) for dynamic role changes
 * SNMP integration for port management
 * Automatic VLAN switching

*Workarounds:*

[options="compact"]
 . *Manual Port Resets:* Physical disconnection/reconnection required
 . *Use AOS-S Switches:* For full PacketFence compatibility
 . *Hybrid Approach:* CX for core, AOS-S for access where CoA is needed

*Alternative Solutions:*

[source,bash]
----
# Force reauthentication via switch CLI
switch# aaa authentication port-access interface 1/1/1 client-limit 1
switch# aaa authentication port-access interface 1/1/1 reauth
----

*Community Reference:*
1. https://sourceforge.net/p/packetfence/mailman/message/36934610/[ArubaOS CX support]

*Problem:* After successful social media authentication (Facebook, Google)^[1]^
Cisco WLC doesn't apply the correct guest role or VLAN.

*Symptoms:*

[options="compact"]
 * Social media authentication completes successfully
 * Guest user receives confirmation but remains in restricted VLAN
 * WLC shows client as authenticated but no role change
 * Client cannot access internet despite successful portal completion
 * PacketFence shows user as registered with correct role
 * WLC client detail shows incorrect or no ACL assignment
 * CoA packets may not be reaching WLC or being processed

*Solution:*

*WLC Configuration Requirements:*

[options="compact"]
 . *Enable CoA on RADIUS Server:*
   - WLC → Security → AAA → RADIUS → Authentication
   - Select PacketFence RADIUS server
   - Check "Support for CoA" checkbox

[options="compact"]
 . *RADIUS Server Configuration:*
   - Verify RADIUS shared secret matches
   - Ensure CoA port 3799 is accessible
   - Check RADIUS server IP is correctly configured

[options="compact"]
 . *ACL and VLAN Verification:*
+
[source,bash]
----
# Check ACL assignment in WLC
(Cisco Controller) > show client detail <client-mac>

# Verify VLAN mapping
(Cisco Controller) > show interface detail <interface-name>
----

*PacketFence Side Verification:*

[source,bash]
----
# Check role assignment in logs
tail -f /usr/local/pf/logs/packetfence.log | grep -i "role"

# Verify CoA is being sent
tcpdump -i any port 3799
----

*Affected Versions:* All PacketFence versions with Cisco WLC integration

*Community Reference:*
1. https://sourceforge.net/p/packetfence/mailman/message/58720739/[Cisco WLC and guest reconnect issue (CoA)]

[[unifi-coa-limitations]]
=== UniFi controller CoA (Change of Authorization) limitations and compatibility

*Problem:* UniFi controller software updates restrict CoA functionality to specific wireless security configurations, breaking existing PacketFence RADIUS-assigned VLAN deployments

*Symptoms:*

[options="compact"]
 * CoA functionality previously working but stops after UniFi controller update
 * CoA options no longer available for non-Enterprise wireless security types
 * MAC authentication with RADIUS-assigned VLANs fails to change user VLAN
 * BYOD networks with VLAN assignment based on group membership not functioning
 * Manual CoA configuration required but not sustainable for production

*Understanding the Limitation:*

*Controller Behavior Change:*

UniFi controller software versions now restrict CoA functionality:
[options="compact"]
 - CoA may only be available for WPA2 Enterprise configurations
 - Non-Enterprise security types lose CoA capability after controller updates
 - This affects MAC authentication and RADIUS-assigned VLAN scenarios

*Affected Network Configurations:*
[options="compact"]
 - MAC authentication with RADIUS-assigned VLANs
 - BYOD networks using Google LDAP registration
 - VLAN assignment based on user group membership
 - Mixed security environments requiring dynamic VLAN assignment

*Workarounds and Alternatives:*

*Option 1: Upgrade to WPA2 Enterprise*
[options="compact"]
 * Configure UniFi network for WPA2 Enterprise
 * Enable RADIUS authentication pointing to PacketFence
 * Verify CoA functionality is restored with Enterprise security

*Option 2: Manual CoA Configuration*
[options="compact"]
 * Note: Manual configuration in text files is possible but not recommended
 * for production environments due to maintenance complexity
 * Consult UniFi documentation for controller-specific CoA settings

*Option 3: Alternative VLAN Assignment Methods*
[options="compact"]
 * Consider switch-based VLAN assignment if UniFi CoA is unavailable
 * Implement static VLAN assignments where dynamic assignment was required
 * Review network architecture to minimize CoA dependency

*Verification Steps:*
[options="compact"]
 * Check UniFi controller version and CoA availability
 * Test RADIUS authentication with VLAN assignment
 * Monitor RADIUS logs for successful/failed VLAN attribute processing
 *  Verify switch configuration supports alternative VLAN assignment methods

*Important Notes:*

CoA functionality should not be dependent on wireless security type from a technical perspective, but UniFi controller software may enforce this limitation. Evaluate controller version compatibility before deployment and consider alternative architectures if CoA is critical.

*Affected Versions:* Specific UniFi controller versions (varies by release)

*Community Reference:*

1. https://sourceforge.net/p/packetfence/mailman/message/59193967/[PacketFence with Unifi and CoA configuration challenges]

[[procurve-switch-basic-configuration]]
=== ProCurve switch basic configuration and integration guidance

*Problem:* ProCurve switches require specific configuration approaches for optimal PacketFence integration, with choice between RADIUS authentication and port security methods

*Symptoms:*

[options="compact"]
 * Uncertainty about whether to use RADIUS or port security for ProCurve integration
 * Port blocking and unblocking not working as expected
 * Node registration and role assignment inconsistencies
 * Switch authentication method not properly configured
 * RADIUS communication issues between ProCurve and PacketFence

*Solution:*

*Step 1: Choose Optimal Authentication Method*

Prefer RADIUS over port security when switch supports it:

[options="compact"]
 * Recommended approach for ProCurve switches:
 * Use RADIUS authentication instead of port security
 * RADIUS provides better integration and role management

[options="compact"]
 * Verify switch RADIUS capabilities:
 * Check ProCurve model documentation for RADIUS support
 * Confirm 802.1X authentication features available

*Step 2: Basic Switch Configuration Requirements*

Configure essential ProCurve settings for PacketFence integration:

[options="compact"]
# Required switch configuration steps:

# 1. Disable Link Up/Down Traps
# Configuration → System → SNMP
# Disable linkup/linkdown trap notifications

# 2. Enable Port Security (if using port security method)
# Configuration → Security → Port Security
# Enable port security on required interfaces

# 3. Configure SSH Credentials
# Configuration → System → SSH
# Enable SSH access for PacketFence management
----

*Step 3: RADIUS Configuration Setup*

Configure RADIUS at switch level for authentication:

----
# RADIUS server configuration:
# Configuration → Security → RADIUS
# Primary RADIUS Server: <PacketFence IP>
# Authentication Port: 1812
# Accounting Port: 1813
# Shared Secret: <configured secret>

# Interface-specific configuration:
# Configuration → Security → 802.1X
# Enable 802.1X on required ports
# Set authentication method to RADIUS
----

*Step 4: PacketFence Switch Configuration*

Add ProCurve switch to PacketFence server configuration:

----
# PacketFence switch configuration:
# Configuration → Network Configuration → Switches
# IP: <switch IP address>
# Description: <descriptive name>
# Type: HP/ProCurve (select appropriate model)
# Mode: Production
# RADIUS Secret: <matching switch secret>
# SNMP Community: <read/write community>
----

*Step 5: Integration Verification*

Test PacketFence and ProCurve integration:

----
# Verify RADIUS communication:
tail -f /usr/local/pf/logs/radius.log

# Test port control from PacketFence:
# Configuration → Network Configuration → Switches
# Test connection and port control functionality

# Monitor node registration:
tail -f /usr/local/pf/logs/packetfence.log | grep -i registration

# Verify role assignment works:
# Check that nodes receive proper VLAN assignment
----

*Configuration Method Comparison:*

**RADIUS Authentication (Recommended):**
- Better role management and VLAN assignment
- More granular control over authentication
- Support for dynamic user/device policies
- Integration with authentication sources

**Port Security (Alternative):**
- Simpler configuration for basic deployments
- Limited role assignment capabilities
- Static port-based control
- Less integration with authentication systems

*Important Notes:*

- Role assignment depends on successful RADIUS request to PacketFence
- Configure specific interfaces to be controlled by PacketFence
- Monitor RADIUS logs during initial configuration for troubleshooting
- Verify network connectivity between switch and PacketFence server

*Affected Versions:* All PacketFence versions with ProCurve support

*Community Reference:*

1. https://sourceforge.net/p/packetfence/mailman/message/37783753/[ProCurve Switch Basic Configuration]

'''
