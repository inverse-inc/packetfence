== Active Directory Integration


[[eap-tls-host-prefix]]
=== Windows machines add "host/" prefix during EAP-TLS

*Problem:* Windows computers prepend "host/" to machine names during
certificate-based authentication, causing authentication failures^[1]^

*Symptoms:*

* Windows machines fail EAP-TLS authentication
* RADIUS logs show usernames like "host/COMPUTERNAME"
* Authentication source configured for plain computer names fails
* Certificate authentication works for users but not computers
* LDAP searches fail when looking for computer objects
* Active Directory shows computers as "host/machinename$"

*Solution:*

*This is normal Windows behavior.* Configure authentication source properly:

*Authentication Source Configuration:*

. *Machine Account Search:* Use `servicePrincipalName` attribute
. *Username Attribute:* Set to handle "host/computername" format
. *Advanced Rules:* Create separate rules for users vs machines
. *Certificate Mapping:* Use `userPrincipalName` for computer objects if needed

*Example Configuration:*
----
# In authentication source settings
Username Attribute: servicePrincipalName
Search Filter: (&(objectClass=computer)(servicePrincipalName=host/*))
----

*Community Reference:*
1. https://sourceforge.net/p/packetfence/mailman/message/58775568/[802.1x Machine Auth with User-Name = 'domain\\hostname$']

[[ad-password-encryption-v14]]
=== Active Directory password encryption issues with v14.1

*Problem:* After upgrading to PacketFence 14.1, domain join status shows "The SAM database on the Windows Server does not have a computer account for this workstation trust relationship"^[1]^

*Symptoms:*

* Domain join appears successful initially but fails later
* Intermittent authentication failures with AD
* Trust relationship errors in domain join status
* Machine accounts show as disabled or missing in AD
* Authentication works initially after domain join but fails after some time

*Solution:*

The issue is related to password encryption changes in v14.1. To resolve:

. *Edit crypto password in configuration:*
  - Go to Configuration → System Configuration → Database
  - Edit the crypto password and put it back in clear text

. *Reload configuration and restart services:*
+
----
/usr/local/pf/bin/pfcmd configreload hard
/usr/local/pf/bin/pfcmd service pf restart
----

. *Re-join domain if necessary:*
+
----
/usr/local/pf/bin/pfcmd domain rejoin <domain_name>
----

*Affected Versions:* v14.1 and later

*Community Reference:*
1. https://sourceforge.net/p/packetfence/mailman/message/59198876/[Cluster Integration with AD - SAM database error]

[[domain-join-no-logon-servers]]
=== Domain join fails with "No logon servers available"

*Problem:* PacketFence cannot join Active Directory domain, showing "No logon
servers are currently available" error^[1]^

*Symptoms:*

* Domain join process fails during setup
* Error message: "No logon servers are currently available"
* DNS lookup failures for domain controllers
* Time synchronization errors between PacketFence and AD
* Connection timeout to AD ports (389, 636, 88)
* `/usr/local/pf/logs/packetfence.log` shows domain join errors
* `wbinfo -P` shows no available domain controllers

*Solution:*

*Network and DNS troubleshooting:*

. *DNS Resolution Test:*
+
----
nslookup domain-controller.domain.com
dig domain-controller.domain.com
----

. *Connectivity Test:*
+
----
telnet domain-controller.domain.com 389
telnet domain-controller.domain.com 636
----

. *Time Synchronization:*
+
----
ntpdate domain-controller.domain.com
# Or configure NTP permanently
----

*Advanced Solutions:*

* *Use IP addresses* instead of hostnames for domain controllers
* *Check firewall rules* for ports 389, 636, 88, 135, and high ports (1024-65535)
* *Verify DNS suffixes* in `/etc/resolv.conf`
* *Test with different domain controller* if multiple are available

*Affected Versions:* All PacketFence versions with AD integration

*Community Reference:*
1. https://sourceforge.net/p/packetfence/mailman/message/58743484/[Getting Started step FAILS: 5.2. Connecting PacketFence to Microsoft Active Directory]
2. https://sourceforge.net/p/packetfence/mailman/message/36018327/[Winbind troubleshooting and domain connectivity issues]

[[machine-account-permissions]]
=== Machine account permissions insufficient

*Problem:* Domain join fails with access denied errors, insufficient
permissions to create machine accounts^[1]^

*Symptoms:*

* Domain join fails with "Access denied" errors
* Error messages about insufficient permissions
* Account cannot create computer objects in target OU
* Authentication works for users but domain join fails
* Event logs on domain controller show access denied events
* `wbinfo -t` command fails after attempted join
* NTLM auth API returns HTTP code 422 with machine account test failures
* Error message: "Access Denied... has not been granted those access rights"
* Machine account creation fails during PacketFence AD integration setup

*Solution:*

*Account Permission Requirements:*

The domain join account needs these permissions:

. *"Create Computer Objects"* in target OU
. *"Join computers to domain"* user right
. *Write permissions* on computer objects in AD

*Recommended Solutions:*

*Option 1: Temporary Domain Admin*
----
# Use Domain Admin account for initial setup
# Change to service account after successful join
----

*Option 2: Delegated Permissions*
----
# In Active Directory Users and Computers:
# 1. Right-click target OU → Delegate Control
# 2. Add service account
# 3. Grant "Create Computer Objects" permission
----

*Option 3: Pre-created Computer Account*
----
# Pre-create computer account in AD
# Grant service account "Reset Password" permission
----

*Troubleshooting Steps:*

Before attempting domain join, verify network connectivity:

----
# Test basic AD connectivity
ping domain-controller-ip

# Test LDAP ports
telnet domain-controller 389
telnet domain-controller 53

# Verify DNS resolution
nslookup domain.com
----

*Verification Commands:*
----
wbinfo -t          # Test secure channel
wbinfo -P          # Ping domain controllers
wbinfo -u          # List domain users (test connection)
----

*Root Cause Analysis:*

HTTP 422 errors during machine account testing indicate the AD service account lacks "correct right elevation to create the PF object in the AD". Ensure the account has proper OU permissions before attempting PacketFence domain integration.

*Affected Versions:* All PacketFence versions with AD integration

*Community Reference:*

1. https://sourceforge.net/p/packetfence/mailman/message/59220986/[AD machine account permissions error 3221225506]

2. https://sourceforge.net/p/packetfence/mailman/message/59228778/[PacketFence AD integration access denied troubleshooting]

[[username-attribute-config]]
=== Username attribute configuration issues

*Problem:* Users cannot authenticate, or authentication works inconsistently
with different username formats^[1]^

*Solution:*

*Choose appropriate username attributes:*

*sAMAccountName (Traditional):*
* Format: `username`
* Use for: Standard domain authentication
* Best for: Windows environments

*userPrincipalName (Modern):*
* Format: `username@domain.com`
* Use for: Mixed environments, computer accounts
* Best for: Modern Active Directory setups

*Configuration Examples:*

*For User Authentication:*
----
Username Attribute: sAMAccountName
Search Filter: (&(objectClass=user)(sAMAccountName=%u))
----

*For Computer Authentication:*
----
Username Attribute: userPrincipalName
Search Filter: (&(objectClass=computer)(userPrincipalName=%u))
----

*Mixed Environment Setup:*
----
# Create two authentication sources:
# Source 1: Users with sAMAccountName
# Source 2: Computers with userPrincipalName
# Bind both to same connection profile
----

*Troubleshooting Username Length Limitations:*

For usernames longer than 20 characters experiencing authentication failures:

----
# Verify UPN format is correct
# Example: firstname.lastname@domain.com should be valid UPN

# Test authentication source configuration
/usr/local/pf/bin/pftest authentication username@domain.com password

# Check LDAP attribute retrieval
ldapsearch -x -H ldap://domain-controller \
  -b "DC=domain,DC=com" \
  -D "username@domain.com" -W \
  "(userPrincipalName=firstname.lastname@domain.com)"
----

*Note:* If authentication fails despite proper UPN configuration, verify that the userPrincipalName attribute is correctly formatted and that PacketFence authentication source accepts the full UPN format rather than truncating at 20 characters.

*Affected Versions:* All PacketFence versions with AD integration

*Community Reference:*

1. https://sourceforge.net/p/packetfence/mailman/message/59218208/[Username attribute configuration - 20 character limit issue]

2. https://sourceforge.net/p/packetfence/mailman/message/59218196/[802.1X authentication fails for usernames longer than 20 characters]

[[ad-nt-error-codes-v14]]
=== Active Directory authentication fails with NT error codes

*Problem:* Authentication against Active Directory fails with specific NT error codes after upgrading to v14.x^[1]^

*Symptoms:*

* Users cannot authenticate via 802.1X or captive portal
* RADIUS logs show NT error codes in authentication attempts
* Domain join appears successful but authentication fails
* Error messages in `/usr/local/pf/logs/packetfence.log`
* SSSD service may report connection issues
* `wbinfo -t` command may fail with trust relationship errors

*Common Error Codes:*

*NT Error 3221225762* ("Syntactically invalid computer name")::
Verify Active Directory FQDN configuration in domain settings. Ensure hostname format matches AD requirements.

*NT Error 3221225506* ("Access denied")::
The account used for domain join lacks sufficient permissions to create machine objects in Active Directory.

*Solution:*

. *For FQDN errors:* Check System Configuration → Domain Settings → DNS Name
. *For access errors:* Use account with "Create Computer Objects" permission
. *Verify domain join status:* Test with `wbinfo -t`
. *Check connectivity:* Ensure ports 389, 636, 88, 135 are accessible

*Affected Versions:* PacketFence v14.x

*Community Reference:*
1. https://sourceforge.net/p/packetfence/mailman/message/58829055/[NT Error 3221225762 on PacketFence v14 using AD]

[[active-directory-first-connection]]
=== 802.1X authentication fails for new Active Directory accounts

*Problem:* 802.1X authentication fails for new Active Directory user accounts that have never logged into the computer before, while working for previously logged-in accounts^[1]^

*Symptoms:*

* New AD user accounts cannot authenticate from Windows login screen
* Previously used accounts authenticate successfully
* Computer cannot reach Active Directory during initial authentication
* Authentication works after user has logged in locally at least once

*Solution:*

*Step 1: Enable Computer Authentication*

Configure 802.1X for both computer and user authentication:

----
# In Group Policy or local security policy:
# Computer Configuration → Security Settings → Wired Network Policies
# Enable "Computer authentication" option
# Set authentication mode to "Computer authentication followed by user authentication"
----

*Step 2: Verify Network Connectivity to Domain Controllers*

Ensure computers can reach domain controllers during pre-login:

----
# Test connectivity to domain controller:
ping domain-controller-ip

# Verify DNS resolution works:
nslookup domain.com

# Check that 802.1X allows computer-level traffic to AD
----

*Step 3: Configure Computer Authentication in PacketFence*

Allow computer accounts in authentication source:

----
# Configuration → Policies → Authentication Sources
# Active Directory source settings:
# Check "Allow computer accounts" option
# Verify computer object authentication is enabled
----

*Affected Versions:* All PacketFence versions with AD integration

*Community Reference:*
1. https://sourceforge.net/p/packetfence/mailman/message/37643836/[802.1x AD first connexion]

[[ad-integration-best-practices]]
=== Active Directory integration best practices for reliable authentication

*Problem:* Multi-domain controller environments cause authentication failures and configuration complexity, requiring specific setup practices to ensure reliable AD integration

*Symptoms:*

* "NT_STATUS_INVALID_COMPUTER_NAME" errors in NTLM authentication
* "ad_server: Please specify the IPv4" configuration warnings
* Intermittent authentication failures in multi-DC environments
* Round-robin DNS causing connection issues to domain controllers
* Authentication working with some DCs but failing with others
* Domain join process succeeding but authentication inconsistent

*Solution:*

*Best Practice 1: Use Specific Domain Controller Configuration*

Avoid round-robin DNS and use individual domain controller details:

----
# Instead of using multi-IP FQDN records, specify individual DC:
# Domain Controller: dc1.domain.com (not domain.com)
# Verify DNS resolves to single IP:
nslookup dc1.domain.com

# Test connectivity to specific DC:
telnet dc1.domain.com 389
ping dc1.domain.com
----

*Best Practice 2: Configure Both FQDN and IP Fields*

PacketFence v13.1+ requires explicit IP configuration:

----
# In PacketFence AD configuration:
# Active Directory FQDN: dc1.domain.com
# Active Directory IP: 192.168.1.10

# Verify configuration consistency:
dig dc1.domain.com
# Should return the IP specified in AD configuration
----

*Best Practice 3: Pre-Deployment Verification*

Verify DNS resolution and connectivity before configuration:

----
# Test DNS resolution consistency
for i in {1..5}; do nslookup domain-controller.domain.com; done

# Verify LDAP connectivity
ldapsearch -x -H ldap://dc1.domain.com -b "DC=domain,DC=com" -s base

# Test authentication connectivity
telnet dc1.domain.com 389
telnet dc1.domain.com 636
----

*Best Practice 4: Multi-Domain Controller Deployment*

For environments requiring multiple DCs, configure redundancy properly:

----
# Option 1: Configure primary and backup DCs separately
# Primary: DC1 with specific IP
# Backup: Separate authentication source for DC2

# Option 2: Use load balancer with consistent routing
# Configure load balancer to maintain session persistence
# Ensure same client always hits same DC during auth session
----

*Configuration Verification:*

----
# Test domain join with specific configuration
/usr/local/pf/bin/pfcmd domain test domain.com

# Verify NTLM authentication works consistently
tail -f /usr/local/pf/logs/packetfence.log | grep -i ntlm

# Check for configuration warnings
/usr/local/pf/bin/pfcmd configreload hard
----

*Future Improvements:*

PacketFence developers are improving the process to be more resilient to multi-DC environments. Future versions will handle multiple domain controllers more gracefully.

*Prevention:*

- Always use specific domain controller FQDNs rather than domain-level DNS records
- Explicitly configure IP addresses even when FQDN is provided
- Test authentication thoroughly before production deployment
- Monitor NTLM authentication logs for consistency

*Affected Versions:* PacketFence v13.1+ (FQDN and IP requirements)

*Community Reference:*

1. https://sourceforge.net/p/packetfence/mailman/message/58791013/[Best practice for reliable Active Directory Integration]
