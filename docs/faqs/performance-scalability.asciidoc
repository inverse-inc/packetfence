== Performance & Scalability


[[large-deployment-cpu-issues]]
=== Large deployments cause CPU performance problems

*Problem:* PacketFence deployment with 1000+ devices experiences high CPU
utilization and performance degradation^[1]^

*Symptoms:*

* System CPU usage consistently above 80-90%
* Slow response times in web interface
* Authentication delays or timeouts
* High load averages (5.0+ on multi-core systems)
* Database connection timeouts
* RADIUS authentication delays
* Fingerbank collector consuming excessive CPU resources
* Memory usage continuously growing

*Solution:*

*Infrastructure Scaling:*

*Hardware Recommendations for Large Deployments:*

*14,000+ Clients:*
* CPU: 8+ cores minimum
* RAM: 32GB+ recommended
* Storage: SSD for database and logs
* Network: Gigabit minimum, 10Gb preferred for clusters

*Fingerbank Collector Optimization:*
----
# Disable TCP packet handling to reduce CPU load:
# Edit fingerbank-collector service configuration:
# /etc/systemd/system/fingerbank-collector.service.d/override.conf

[Service]
Environment=COLLECTOR_DISABLE_TCP_HANDLER=true

# Reload and restart service:
systemctl daemon-reload
systemctl restart fingerbank-collector
----

*Database Performance Tuning:*
----
# MariaDB optimization for large deployments:
# /etc/mysql/mariadb.conf.d/50-server.cnf

[mysqld]
innodb_buffer_pool_size = 16G      # 50-70% of available RAM
innodb_log_file_size = 512M
innodb_log_buffer_size = 64M
max_connections = 1000
query_cache_size = 256M
table_open_cache = 2048

# Apply changes:
systemctl restart mariadb
----

*Cluster Architecture Consideration:*
----
# For 5000+ concurrent users, consider cluster deployment:
# - 3+ nodes minimum for high availability
# - Load balancer for RADIUS requests
# - Shared database backend (Galera cluster or external MySQL)
----

*Monitoring and Maintenance:*
----
# Regular performance monitoring:
htop                              # CPU and memory usage
iostat -x 1                      # Disk I/O monitoring
mysqladmin processlist           # Database connection monitoring
/usr/local/pf/bin/pfcmd service pf status  # Service health
----

*Community Reference:*
1. https://sourceforge.net/p/packetfence/mailman/message/58786190/[PacketFence system requirements for a large deployment]

[[fingerbank-collector-cpu]]
=== Fingerbank collector high CPU usage and performance issues

*Problem:* The fingerbank-collector service causes various CPU-related performance issues including excessive resource consumption during device registration, service restart loops, and system unresponsiveness during peak usage^[1]^

*Symptoms:*

* `fingerbank-collector` process shows high CPU usage in `top` or `htop`
* CPU load reaching very high levels (e.g., 15+ on multi-core systems)
* Fingerbank collector service restarts continuously
* System load averages elevated during high network activity
* Slow response times during device registration
* Delays in SMS confirmations and email delivery
* Role assignments taking excessive time
* Performance degradation during peak usage periods (25+ registrations per minute)
* Service restart loops in system logs
* CPU spikes to 90%+ during device detection
* System becomes unresponsive during high device registration activity
* High CPU usage persists even when TCP fingerprinting is disabled

*Solution:*

*Step 1: Add Fingerbank API Key (Primary Fix)*

Configure Fingerbank API key to resolve CPU bottlenecks:

----
# In PacketFence web interface:
# Configuration → Compliance → Fingerbank Profiling
# Add your Fingerbank API key in the appropriate field
# Save the configuration

# Restart fingerbank-related services:
systemctl restart packetfence-fingerbank-collector
systemctl restart packetfence
----

*Step 2: Disable TCP Handler (If API Key Insufficient)*

Configure collector to disable problematic TCP handler:

----
# Create systemd override directory (use correct service name):
mkdir -p /etc/systemd/system/packetfence-fingerbank-collector.service.d

# Create override configuration:
cat > /etc/systemd/system/packetfence-fingerbank-collector.service.d/override.conf << EOF
[Service]
Environment=COLLECTOR_DISABLE_TCP_HANDLER=true
EOF

# Reload systemd and restart service:
systemctl daemon-reload
systemctl restart packetfence-fingerbank-collector
----

*Step 3: Verify Service Stability and Performance*

Monitor service for restart loops and CPU usage improvement:

----
# Monitor service status:
systemctl status packetfence-fingerbank-collector

# Check service logs for restart loops:
journalctl -u packetfence-fingerbank-collector -f

# Monitor CPU usage improvement:
htop | grep fingerbank
top -p $(pgrep fingerbank-collector)

# Monitor overall system performance:
top -u pf

# Check fingerbank logs for proper API key usage:
tail -f /usr/local/pf/logs/fingerbank.log

# Verify improved response times during registration:
tail -f /usr/local/pf/logs/packetfence.log | grep -i registration
----

*Step 4: Advanced Configuration Options*

Additional tuning for performance optimization:

----
# Advanced environment variables for tuning:
[Service]
Environment=COLLECTOR_DISABLE_TCP_HANDLER=true
Environment=COLLECTOR_DISABLE_UDP_HANDLER=false
Environment=COLLECTOR_WORKERS=2

# Reduce collection frequency if needed:
Environment=COLLECTOR_INTERVAL=300
----

*Step 5: Optimize Fingerbank Configuration*

Adjust fingerbank settings in PacketFence interface:

----
# In PacketFence admin interface:
# Configuration → System Configuration → Fingerbank Settings
# Disable unnecessary fingerprinting methods
# Reduce fingerbank update frequency if needed

# Check fingerbank logs:
tail -f /usr/local/pf/logs/fingerbank.log
----

*Step 6: Alternative - Complete Disable if Not Critical*

If fingerprinting isn't essential for your deployment:

----
# Disable fingerbank collector entirely:
systemctl stop packetfence-fingerbank-collector
systemctl disable packetfence-fingerbank-collector

# Verify PacketFence still functions without device fingerprinting
----

*Performance Impact:*
* *API Key Solution:* Dramatic improvement in system performance, resolving CPU bottlenecks
* *TCP Handler Disable:* 60-80% CPU reduction typical
* *What you lose:* Advanced TCP-based device fingerprinting
* *What you keep:* DHCP-based device identification, basic fingerprinting
* *Service stability:* Eliminates restart loops

*Affected Versions:* All PacketFence versions with Fingerbank integration

*Community Reference:*
1. https://sourceforge.net/p/packetfence/mailman/message/36496649/[Fingerbank: High CPU Usage - no local db entries?]

[[cluster-service-restart-limitation]]
=== No cluster-wide service restart mechanism available

*Problem:* PacketFence clusters lack a built-in mechanism to restart services across all cluster nodes simultaneously, requiring manual intervention on each node^[1]^

*Symptoms:*

* No single command to restart services on all cluster nodes
* Manual SSH required to each server for service management
* Certificate updates require individual node synchronization
* Service restarts must be performed node-by-node
* Potential for configuration drift between nodes during maintenance

*Solution:*

*Current Workaround - Manual Node Management:*

*Step 1: SSH-Based Service Restart*

Restart services manually on each cluster node:

----
# SSH to each cluster node and restart services:
ssh node1.cluster /usr/local/pf/bin/pfcmd service pf restart
ssh node2.cluster /usr/local/pf/bin/pfcmd service pf restart
ssh node3.cluster /usr/local/pf/bin/pfcmd service pf restart

# Alternative - use web interface on each node:
# https://node1.cluster:1443/admin/services
# https://node2.cluster:1443/admin/services
----

*Step 2: Certificate Synchronization*

For certificate updates, sync manually across nodes:

----
# From master node, sync certificates:
/usr/local/pf/bin/cluster/sync --file /usr/local/pf/conf/ssl/server.pem --as-master

# Verify certificate on each node:
openssl x509 -in /usr/local/pf/conf/ssl/server.pem -text -noout
----

*Step 3: Configuration Reload*

Ensure configuration consistency across cluster:

----
# On each node, reload configuration:
/usr/local/pf/bin/pfcmd configreload hard

# Verify cluster synchronization:
/usr/local/pf/bin/cluster/maintenance
----

*Future Enhancement Needed:*
This is a known limitation. A cluster-wide service management feature would be valuable for future PacketFence releases.

*Affected Versions:* All PacketFence versions with clustering

*Community Reference:*
1. https://sourceforge.net/p/packetfence/mailman/message/37377556/[Restarting service in a cluster]

[[high-cpu-performance-k12-environment]]
=== High CPU usage in large K-12 deployment with 14,000+ devices

*Problem:* PacketFence deployment experiences CPU spikes up to 90% during peak usage times in large educational environments with thousands of concurrent devices^[1]^

*Symptoms:*

* CPU usage spikes to 90% during peak hours (school start times)
* Slow authentication responses during high load periods
* Current setup: 8 cores, 32GB RAM serving 14,000+ clients
* Performance degradation affects user experience
* Authentication timeouts during peak usage

*Solution:*

*Step 1: Implement Cluster Architecture*

For 14,000+ devices, implement a cluster deployment:

----
# Recommended cluster architecture for K-12:
# - 3 nodes minimum for high availability
# - Load balancer for RADIUS requests
# - Shared database backend

# Example cluster node specifications:
# Each node: 16+ cores, 64GB+ RAM
# Database: Dedicated server or Galera cluster
# Load balancer: HAProxy or hardware solution
----

*Step 2: Optimize Database Performance*

Tune MySQL/MariaDB for high concurrent load:

----
# Database optimization for high load:
[mysqld]
innodb_buffer_pool_size = 32G      # 50-70% of available RAM
max_connections = 2000
query_cache_size = 512M
table_open_cache = 4096
innodb_thread_concurrency = 16
innodb_read_io_threads = 8
innodb_write_io_threads = 8

# Apply changes:
systemctl restart mariadb
----

*Step 3: Implement RADIUS Load Balancing*

Configure RADIUS load balancing for authentication:

----
# HAProxy configuration for RADIUS load balancing:
backend packetfence_radius
    mode tcp
    balance roundrobin
    server pf1 10.0.1.10:1812 check
    server pf2 10.0.1.11:1812 check
    server pf3 10.0.1.12:1812 check
----

*Step 4: Monitor and Scale*

Implement monitoring for proactive scaling:

----
# Performance monitoring setup:
# Monitor CPU, memory, disk I/O, and network
# Set alerts for CPU >70%, memory >80%
# Monitor authentication response times

# Example monitoring commands:
htop                                    # CPU and memory
iostat -x 1                            # Disk I/O
ss -tuln | grep 1812                   # RADIUS connections
/usr/local/pf/bin/pfcmd service pf status  # Service health
----

*Note:* For environments with 15,000+ devices, users report success with 3-node clusters and proper load balancing.

*Affected Versions:* All PacketFence versions

*Community Reference:*
1. https://sourceforge.net/p/packetfence/mailman/message/58786190/[PacketFence system requirements for a large deployment]
