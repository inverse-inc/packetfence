//=== Generic HTTP

The Generic HTTP provisioner allows you to integrate any HTTP JSON API (MDM,
EDR, asset inventory, ...) that is not natively supported by PacketFence. You
define the HTTP request to perform for a device in the configuration and a jq
query that decides, from the JSON response, whether or not the device is
compliant.

==== Configure the provisioner

In the PacketFence administration interface, go in _Configuration -> Advanced
Access Configuration -> Provisioners_ and create a new provisioner of type
*Generic HTTP*.

===== The request

The *URL*, the *headers* and the *body* of the request are templates. The
following variables are available:

 * `$mac`: the MAC address of the device being checked
 * `$node.<attribute>`: any attribute of the node (ex: `$node.pid`,
   `$node.category`, `$node.computername`, ...), see <<generic_http_available_fields>>
   for the complete list
 * `$tls.<attribute>`: the TLS certificate data PacketFence last recorded for
   the device (ex: `$tls.TLSClientCertSerial`, `$tls.TLSClientCertCommonName`),
   the same data the jq query gets as `$tls`, see
   <<generic_http_available_fields>>. An attribute is empty when nothing is
   recorded for the device.

For example:

  https://mdm.example.com/api/v1/devices?mac=$mac

Because `$` introduces a variable, a literal `$` must be doubled. This matters
for API tokens, which often contain one:

  Authorization: Bearer sk-abc$$def

written with a single `$`, the `$def` would be read as an (empty) variable and
the token would be sent truncated. The provisioner refuses to save a URL,
header or body that references a variable other than `$mac`, `$node.*` and
`$tls.*`, or
a template function it does not support.

===== Escaping values

Node and TLS attributes are inserted as is. Two template functions are provided to
escape them where the surrounding syntax requires it. Function calls use the
`${function(...)}` syntax.

In a JSON *body*, use `json_quote()` instead of writing the surrounding quotes
yourself. The function returns a complete JSON string, quotes included, with
the value escaped. Given a `pid` containing a quote or a backslash:

  {"user": ${json_quote($node.pid)}}

In a *URL*, use `url_quote()` to percent-encode a value used as a path segment
or a query parameter:

  https://mdm.example.com/api/v1/devices/$mac?user=${url_quote($node.pid)}

Everything outside the RFC 3986 unreserved characters is encoded, so a value
containing `&`, `=` or `#` cannot add or change a query parameter.

Do not put untrusted values in a header name, and do not use `url_quote()` on
a header value: header values are not URL-encoded. Header names and values are
instead validated so that a value containing a line break cannot inject a
header.

The *headers* are defined one per line using the `Name: value` syntax. Both
the name and the value are templates. For example:

  Authorization: Bearer my-api-token
  X-Owner: $node.pid

The *body* is only sent for POST, PUT and PATCH requests and defaults to the
`Content-Type` defined in the provisioner unless a `Content-Type` header is
explicitly defined in the headers.

When a *username* and *password* are defined, they are sent using HTTP basic
authentication unless an `Authorization` header is explicitly defined in the
headers.

===== TLS

When the server uses a certificate that is not trusted by the system, you can
upload a *CA certificate* used to verify the server certificate. A *client
certificate* and *client key* can also be uploaded when the server requires
mutual TLS. Verification of the server certificate can be completely disabled
with the *Verify TLS* toggle although this is not recommended.

===== The jq query

The JSON response of the server is evaluated with the *JQ query* of the
provisioner. The device is authorized when the query returns a truthy value
following the jq semantics: every result that is not `null` or `false` is
truthy (including `0` and `""`), an empty result set is falsy.

For example, given the following response:

  {"devices": [{"mac": "aa:bb:cc:dd:ee:ff", "status": "enrolled"}]}

the following query authorizes the device when the status of the first device
is `enrolled`:

  .devices[0].status == "enrolled"

and the following one authorizes it as soon as at least one device matched:

  .devices | length > 0

The device being checked is available to the query as three jq variables,
the same three the request templates get:

 * `$mac`: the MAC address of the device
 * `$node`: the attributes of the node, as an object (ex: `$node.pid`,
   `$node.category`, `$node.computername`, ...). It is `null` when the device
   is not a known node.
 * `$tls`: the TLS certificate data PacketFence last recorded for the device
   from the RADIUS audit log of its TLS-based EAP authentications, as an
   object. The client certificate is under the `TLSClientCert*` keys (ex:
   `$tls.TLSClientCertSerial`, `$tls.TLSClientCertCommonName`,
   `$tls.TLSClientCertIssuer`, `$tls.TLSClientCertSubjectAltNameEmail`,
   `$tls.TLSClientCertExpiration`) and the certificate that issued it under the
   `TLSCert*` keys. It is `null` when nothing is recorded for the device.

See <<generic_http_available_fields>> for every attribute of `$node` and `$tls`.

This is what you want when the server answers about more than the one device
asked about, or when the answer has to be checked against what PacketFence
already knows. For example, to pick the entry of the device out of a list the
server returned:

  .devices | any(.mac == $mac and .status == "enrolled")

or to require that the owner the server reports is the one the node is
registered to:

  .assigned_user == $node.pid

or to require that the certificate the device authenticated with is the one
the server issued to it:

  .certificate.serial == $tls.TLSClientCertSerial

NOTE: The query is evaluated with jq (through the JQ::XS Perl library), so the
full jq language is available, with two restrictions. The query cannot pull
definitions in from `.jq` files on disk: an `include` or an `import` is refused
when the provisioner is saved. And it cannot read the environment of the
process evaluating it, which holds the credentials of the daemon: `env` and
`$ENV` are both an empty object, so `env.FOO` and `$ENV.FOO` are `null`
whatever `FOO` holds.

NOTE: A query that does not compile is logged and treated as a failed check. A
response that is not valid JSON and a jq runtime error are logged as a
communication failure instead, so a server answering something unexpected does
not deauthorize the device.

`$tls.<attribute>` in the request templates and in the jq query.
An attribute that is not set for the device is empty in a template and `null`

===== Testing the jq query

The *Test JQ query* field of the provisioner allows you to validate your query
without contacting the server: paste a sample JSON response in the field and
click 'Test'. The result of the evaluation (pass or fail along with the raw
results of the query) is displayed under the field.

A query using `$mac`, `$node` or `$tls` can be tested against a real device:
enter its MAC address in the *Test node* field above. The node and its TLS
data are looked up in the database and handed to the query exactly as they
would be during an authorization, and what they hold is displayed with the
result of the test, so the attributes the query reads can be checked against
what the node actually carries. Leaving the field empty runs the query with
`$mac`, `$node` and `$tls` all `null`.

==== Enforcement

Like any other provisioner, the compliance check can be enforced during RADIUS
authentication and on the captive portal with the *Enforce* toggle, devices
can be automatically registered with *Auto register* and a role can be applied
with *Apply role*.
