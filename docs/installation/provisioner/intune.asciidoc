==== Configure from the Azure portal

Connect to Azure portal and verify Intune licenses.

===== Creating the application

After portal login, create application to allow Graph API access.

Click 'Azure Active Directory' > 'App registrations' > 'New registration'

image::Azure_Application_1.png[scaledwidth="100%",alt="Azure add application"]

Set application name (e.g., PacketFence), choose 'Supported account types':
'Accounts in this organizational directory only', click 'Register'

image::Azure_Application_2.png[scaledwidth="100%",alt="Azure define application"]

On next page, copy 'Application (client ID)' and 'Directory (tenant ID)' (needed
for provisioner definition).

image::Azure_Application_3.png[scaledwidth="100%",alt="Azure ID"]

Click 'Certificates & secrets' > 'New client secret' for application password
(save immediately; won't be available later).

image::Azure_Application_4.png[scaledwidth="100%",alt="Azure Password"]

Add API permissions: click 'API permissions' > 'Microsoft Graph', select
'Application permissions', add:

 Device.ReadWrite.All
 DeviceManagementManagedDevices.Read.All

And click on 'Grant admin consent for (Name of your app)'

==== Configure PacketFence

===== Create a new provisioner

Login to the admin interface, then go to _Configuration -> Advanced Access
Configuration -> Provisioners_.
Click 'Add provisioner' then select Microsoft Intune.

image::intune-pf-config.png[scaledwidth="100%",alt="Intune PacketFence configuration"]

Now configure this new provisioner with the information you got above.

[options="compact"]
* The Provisioning ID is the friendly name of the provisioner.
* The Application ID is the 'Application (client ID)'.
* The Application Secret is the 'Client secret'.
* The Tenant ID is the 'Directory (tenant ID)'.
* The Client Secret is the secret of the application you created in the developer account.
* The default host should work.
* The default Login URL should work. 
* The port and protocol should be left to default.
* The 'Agent download URI' should be ok.
* 'Device lookup' selects how devices are found in Intune; see below.
* Authorized domains need to be adapted to allow the device to reach the download URI (per example google play needs multiple domains to be able to install the agent).

===== Matching devices in Intune

To check compliance, PacketFence has to find the connecting device in
Intune. The *Device lookup* setting lists the methods it tries, in
order:

[cols="1,2",options="header"]
|===
| Method | What it matches
| Azure AD device ID | The common name (CN) of the EAP-TLS client certificate, or the 802.1X username, is the Azure AD / Entra device ID. This is the case with an Intune SCEP or PKCS profile whose subject is `CN={{AAD_Device_ID}}`.
| Intune device ID | Same, with a subject of `CN={{DeviceId}}` (the Intune managed device ID).
| Device name | The host name in an 802.1X machine identity (`host/name.domain`, as sent by Windows machine authentication) is the Intune device name.
| MAC address | The historical method: the MAC of the connecting interface is the Wi-Fi or Ethernet MAC Intune recorded for the device.
|===

Intune records a single Wi-Fi MAC and a single Ethernet MAC per device
— typically the built-in adapters. A laptop connecting through a
docking station, a USB adapter or any other interface is therefore
*not found* by MAC address, and neither are devices whose first-seen
adapter was a virtual one. Whenever devices authenticate with EAP-TLS,
put one of the device ID methods first and keep *MAC address* last as
a fallback: the device ID lookups are a single filtered Graph query,
while the MAC lookup walks the whole device list.

During RADIUS authentication, the certificate CN and the username of
the current request are used. Outside RADIUS (for example the
_Enforce provisioning_ security event action), PacketFence uses the
last 802.1X username of the node. The 802.1X username comes from the
attributes listed in _Configuration -> System Configuration -> RADIUS
-> General -> Username attributes_, which prefer the certificate
subject alternative names (UPN, DNS) over the CN. With a certificate
that carries a SAN, the device ID methods therefore only work during
RADIUS authentication, where the CN is read directly.

*Device name* is weaker than the device ID methods: a device name is
not unique in Intune and isn't bound to the certificate. PacketFence
only uses the name from an 802.1X machine identity, never the DHCP host
name (the client chooses it), and doesn't use a name shared by several
devices in Intune. Prefer the device ID methods whenever devices use
EAP-TLS.

A device found by none of the methods is treated as not enrolled: it
is not compliant, the *Non compliance security event* is raised if one
is configured, and no `intune` data is available to the rules.

TIP: The Azure AD authentication source can use the same
`CN={{AAD_Device_ID}}` certificate to check group membership; see
_Using Azure AD EAP-TLS machine authentication_ in the Azure AD
section of this guide.

===== Add the provisioner to the profile

Now that you have created the provisioner, go in the 'Connection Profiles' menu
on the left and select the default portal.
Click 'Add Provisioner' and select the new Microsoft Intune provisioner that was
created earlier.

image::intune-portal.png[scaledwidth="100%",alt="Intune portal configuration"]

==== Testing

You can now test that the installation of the Microsoft Intune client is
mandatory after the device registration.
Connect a device to your test network and register like you normally would.
At the end of the registration process, you will be presented a page asking you
to install the Intune client on your device.
After you install the client click continue. If your access is enabled then this
means the connectivity between PacketFence and Azure is good.
