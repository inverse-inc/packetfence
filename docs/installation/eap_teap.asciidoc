//== PacketFence Certificates (for v11.2 and later)

=== Introduction

==== Context and Objectives of the Documentation

Since PacketFence v16.0, we introduced EAP-TEAP support, EAP-TEAP is considered as a faster and next generation of EAP-PEAP.
As EAP-TEAP is still being developed rapidly, it may not be fully supported on all your network devices or platforms.

It is tested and known to work on
 1. Windows 10 (22H2+) / 11 (as TEAP client)
 2. Windows Server 2016 (limited support), Windows Server 2019 (limited support) and Windows Server 2022.
 3. some Cisco Devices running ISE 2.7 Patch2+
 4. some versions of eapol_test (currently, latest devel build)

It is known not to work with:
 1. some versions of eapol_test (2.11 or earlier)
 2. some versions of wpa_supplicant (2.11 or earlier)
 3. iOS / MacOS (not supported yet)

==== Supported inner methods

Windows by default supports EAP-MSCHAPv2 and EAP-TLS when you configure 802.1x client and TEAP.
PacketFence supports EAP-MSCHAPv2 and EAP-TLS as inner methods. Each TEAP profile uses one inner method per
identity type (see *Default EAP Type*, *User EAP Type* and *Machine EAP Type* below): the shipped "Default"
profile only requests the user identity and authenticates it with EAP-TLS. To use EAP-MSCHAPv2, create a TEAP
profile with the EAP types set to MSCHAPv2.

==== EAP chaining

One of the most enticing feature that TEAP brings to us is EAP chaining, it allows you to authenticate both user identities
and machine identities in a single EAP session, which is faster and more efficient.
If eap chaining is enabled, you are expected to provide both "machine identity" and "user identity".

Machine authentication and User authentication both takes either EAP-MSCHAPv2 or EAP-TLS, you can configure your Windows
client to use any of the 4 following combinations:

 1. MSCHAPv2 for both Machine and User
 2. TLS for both Machine and User
 3. MSCHAPv2 for Machine and TLS for User
 4. TLS for Machine and MSCHAPv2 for User

Using both MSCHAPv2 for Machine identity and User identity is one of the most common cases:

When the computer is turned on and booted to log-in screen, machine identity is authenticated.
When the user types in their username and password, user identity is authenticated.
Either authentication failure will result the whole authentication flow to fail.

Therefore, devices knowing the user credentials will *NOT* be granted network access, access is granted only to those
devices joined to Windows domain with correct user credentials.

By default, PacketFence is configured only verifying user identities.

==== Enable TEAP in PacketFence
TEAP is not enabled by default, enable it in the EAP profiles that should offer it.
Create your own TEAP profile first: the shipped "Default" profile is read-only and its *Authority Identity*
must be changed (see below).

Create a TEAP profile

1. Go to *Configuration* -> *System Configuration* -> *RADIUS* -> *TEAP Profiles*
2. Clone the "Default" profile (or create a new one) and give it a name.
3. Set the *Authority Identity* to a value unique to your installation, select the TLS profile you previously
   created or updated, and set the *Identity Types* and the inner EAP types as needed, then save.

image::teap-profiles.jpg[scaledwidth="100%",alt="TEAP Profile Settings"]

Enable TEAP in the EAP profile

1. Go to *Configuration* -> *System Configuration* -> *RADIUS* -> *EAP Profiles*
2. In *EAP Authentication types*, add "TEAP", select your profile in *TEAP Profile* and click save. A TEAP
   profile is required as soon as TEAP is in the authentication types.
3. Restart the radiusd related services if you don't need any other changes.

image::eap-profile.jpg[scaledwidth="100%",alt="EAP Profile Settings"]

TEAP profile settings

*Identity Types* is a setting that tells the RADIUS server which identities should be authenticated. Supported values are "machine", "machine,user", "user", "user,machine".
If you want to authenticate both machine identity and user identity, select "machine,user" or "user,machine".

*Default EAP Type* sets the inner method used to authenticate the user and machine identities. *User EAP Type* and
*Machine EAP Type* are optional and override it for the user identity or the machine identity, for instance EAP-TLS
for the machine and EAP-MSCHAPv2 for the user. The RADIUS server requires that method: a client that asks for
another one inside the tunnel is rejected, so they must match the inner methods configured on your clients. The
shipped "Default" profile sets EAP-TLS as the default EAP type, with no per-identity override.

*Authority Identity* identifies your RADIUS server to TEAP supplicants (per RFC 7170). The shipped default
`packetfence.local` MUST be changed for any production deployment, and MUST be identical across every node
of a cluster. A domain name owned by your organization is recommended. The field accepts only letters,
digits, dot, underscore, dash, and colon. A TEAP profile selected by an EAP profile cannot be deleted.

Restart radiusd service

`/usr/local/pf/bin/pfcmd service radiusd restart`

You should be able to have TEAP support.

==== Limitations
1. If you are running Windows Server 2019 or earlier as a Domain Controller, there will NOT be a GUI way to configure EAP TEAP policies and
  push your policies to your workstations. You might need to manually generate and push a modified XML to enable TEAP.
2. TEAP is supported since Windows 10 (22H2) and later. Please make sure all your workstations are running the compatible version.

Here is a discussion on Cisco Forum showing how to setup and deploy EAP TEAP Profile from an earlier Windows Domain Controller (see limitations 1)

https://community.cisco.com/t5/security-knowledge-base/teap-for-windows-10-using-group-policy-and-ise-teap/ta-p/4134289

==== Realms

It is possible to specify an EAP Profiles for a specific Realm. This provides an extra flexibility for those
who want to enable or disable a feature only for a specific domain.

For example, there are 2 domains, domain A and domain B.
For domain A, we want the most secure policies to be applied. We require TEAP Machine + User authentications.
For domain B, we accept a loose security policy, only user credentials will be validated.

Here are the steps:

 1. we create TEAP profile `teap-domain-A` with "identity types" set to "machine,user"
 2. we create another TEAP profile `teap-domain-B` with "identity types" set to "user"
 3. we go back to EAP Profiles, create two corresponding EAP profile, both enable TEAP, and select `teap-domain-A` and `teap-domain-B` respectively. The EAP Profiles are named "eap-domain-A", "eap-domain-B"
 4. go to Realms, associate the corresponding EAP Profile `eap-domain-A` and `eap-domain-B` to the Realm Domain A and Realm Domain B respectively.
 5. After a restart of related Radiusd services, PacketFence will be able to handle requests against domain A and domain B with associated EAP Profiles.
