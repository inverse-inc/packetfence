===== MS Switch Modules

MS Modules
This is a standard switch module designed to support all the legacy Meraki
Switch series using MS version earlier than v15.x.

Meraki MSv15 
MSv15 module is designed for the switch series operating on MS_OS v15.
Furthermore, it inherits all functionalities from the old "MS220_8" module,
making all the configurations below applicable to MSv15.

NOTE: You should already have one port setup as Uplink, using a mode trunk, with
at least your Registration and Production VLAN allowed on it.

The Meraki switch offer configuration for VLAN enforcement only.

You will need to access the Meraki dashboard to configure your switch. When you
reach it you will need first to create a policy. You can create a "MAC
authentication bypass" or a "802.1X" policy. Depending if you want to
authenticate user via dot1x or MAB. You cannot combine both neither use a
fallback mode on the same port, each port with a policy applied will be
exclusive to MAB or dot1x.

To access the policy creation go to 'Switching->Access Policies' in the Meraki
dashboard menu. From there create a new policy, use the example below to create
your policy.

image::Meraki-switch-policies.png[scaledwidth="100%",alt="Access policies"]

You now need to apply one of your policies to ports. To do so, go to
'Switch->Switch ports' and chose your options. To add a policy you created
earlier, select it in the drop down list in `Access policy`. You need to
configure the port in "mode access", the default access VLAN is not important if
your VLANs are properly configured on PacketFence.

====== Group Policy ACLs (Push ACLs)

A Meraki switch applies to an authenticated client the group policy of the
network named by the `Filter-Id` of the RADIUS Access-Accept, and the _Layer 3
firewall_ rules of that group policy filter the traffic the client sends. With
_Push ACLs_, PacketFence creates a group policy named after each role that has
ACLs, holding the ACLs of the role (_Policies and Access Control -> Roles_, _ACL
in Cisco format_) as L3 firewall rules, updates it when the ACLs change, and
returns the name of the role in `Filter-Id`. The group policies are created
through the Meraki Dashboard API, with the pfsetacls service (Ansible).

In the Meraki dashboard:

* generate a Dashboard API key for an administrator of the organization
  ('Organization->Settings', 'Dashboard API access', then the API key in the
  profile of the administrator), with write access to the network,
* in the access policy of the ports ('Switching->Access policies'), set
  'RADIUS attribute specifying group policy name' to `Filter-Id`.

On the switch in PacketFence (_Policies and Access Control -> Switches_):

* 'Role by Switch Role' (RADIUS tab) enabled, with no role mapping: the name of
  the role is returned as the name of its group policy,
* 'Use Push ACLs' (ACLs tab) enabled,
* 'Web Services' (the ACLs are pushed through the API, not the CLI): any
  'Username' (for example `api`) and the Dashboard API key as 'Password',
* optionally the network ID (`L_...` or `N_...`) as 'Path': without it, the
  network is the one of the Meraki switch whose LAN IP is the IP of the switch
  in PacketFence, in the organizations the API key can read.

Each time the switch or a role is saved, PacketFence pushes the ACLs of every
role (`Switch_ACLS_<switch IP>` in the pfsetacls Semaphore, its log in
[filename]`/usr/local/pf/var/conf/pfsetacls/<switch IP>/`). A group policy with
the name of the role is created, or its L3 firewall rules are replaced (its
other settings are kept). The group policy of a role is deleted when the ACLs
of the role are disabled on the switch, or when the switch is deleted.

The L3 firewall rules of a group policy match the protocol (`tcp`, `udp`,
`icmp` or `ip`), the destination address and the destination port (`eq` or
`range`, of tcp and udp) of an ACL. The source is always the client:

* an ACL with a source address, a source port, TCP flags (`established`), an
  ICMP type, another protocol, or another port operator (`gt`, `lt`, `neq`)
  cannot be a rule. A `permit` is skipped, which only narrows the role; a
  `deny` ends the rules with a deny of all the traffic, and so does a role
  whose ACLs were all skipped or cannot be parsed. [filename]`packetfence.log`
  names the skipped lines,
* `out|` ACLs are not pushed, the rules only filter the traffic the client
  sends,
* the role ACLs follow the Cisco format, where what no line permits is denied,
  while the rules of a group policy allow what no rule matches: PacketFence
  ends the rules with a deny of everything unless the last ACL already matches
  everything (`permit ip any any`, `deny ip any any`).

The switch drops all the traffic of a client whose `Filter-Id` matches no
group policy of the network. A role without ACLs gets no group policy, so no
`Filter-Id` is returned for it: the client is unrestricted, as with the other
switches. Do not map such a role to a switch role unless that group policy
exists in the dashboard.

NOTE: A Catalyst 9300 managed from the Meraki dashboard (C9300-M, or converted
to Meraki management) works with the `Meraki MS v15` type, group policy ACLs
included. It answers the RADIUS Disconnect on port 1700, not 3799: set
'Disconnect Port' to `1700` and disable 'Use CoA' on the switch, it does not
answer the Cisco CoA reauthentication request. The switch only authenticates
the client again when it sends traffic.

====== VoIP phones detection

PacketFence can detect a Cisco IP phone plugged on an MS switch through the CDP
neighbors of the port, read with SNMP (CISCO-CDP-MIB), and return the voice VSA
(`Cisco-AVPair = device-traffic-class=voice`) for it. To use it:

* enable SNMP for the network in the Meraki dashboard ('Network-wide->General',
  'SNMP access'), with a community (v1/v2c) or a user (v3),
* enable 'VoIP' on the switch in PacketFence and set its SNMP read parameters.

NOTE: For SNMPv3, Meraki switches use SHA authentication and DES privacy with the
same password for both.

NOTE: The lookup runs during the RADIUS request. When the switch does not answer
SNMP, PacketFence logs a warning and does not query it again for 10 minutes. If
SNMP is not enabled for the network, disable 'VoIP CDP Detect' on the switch.

The switch lists a phone in its CDP neighbors (SNMP) a few minutes after the port
comes up, usually after the first RADIUS request of the phone. During the first 15
minutes a device is seen on the switch, when it is not detected as a phone,
PacketFence asks the switch to authenticate it again 5 minutes later
(`Session-Timeout = 300` with `Termination-Action = RADIUS-Request`, the port stays
up). A phone gets the voice VSA once its CDP entry is there; other devices get the
regular answer after these 15 minutes.

===== RADSEC

It is possible to use RADSEC between Meraki and PacketFence in order to perform
RADIUS over TCP and encrypted using TLS. Before performing the steps outlined in
this section, make sure you have a working SSID using normal unencrypted RADIUS
by following the steps in the sections above

Then, in order to enable RADSEC, go in your SSID configuration and under 'RADIUS
proxy', select 'Use Meraki proxy' and save the settings.

After saving, check the RADSEC checkbox and save your settings.

Now, on your PacketFence server, you must add the Meraki CA root to the trusted
Certificate Authorities of FreeRADIUS when performing RADSEC. You should
download the Meraki CA certificate from your Meraki dashboard under
Organization->Configure->Certificates and selecting "Download CA" below RadSec
AP Certificates. You can then append the content of this certificate to
/usr/local/pf/raddb/certs/ca.pem on your PacketFence server.

Next, restart radiusd to reload the CA certificates using:

  # /usr/local/pf/bin/pfcmd service radiusd restart

NOTE: RADSEC is done over port 2083 so make sure your server is available via a
public IP address for this port and allows connections from your Meraki cloud
controller. Refer to the Meraki documentation for details.
