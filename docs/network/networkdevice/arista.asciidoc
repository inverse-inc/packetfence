//=== Arista

==== Arista EOS

PacketFence supports Arista EOS switches using RADIUS for MAC Authentication
(MAB) and 802.1X. Dynamic VLAN assignment, RADIUS Change of Authorization (CoA)
and downloadable ACLs (NAS-Filter-Rule) are supported as well as VoIP detection
via LLDP-MED.

The minimum required EOS firmware version is *4.29.1F*. The configuration below
was validated on EOS 4.31.4M (CCS-720DP).

===== Global RADIUS Configuration

Define the PacketFence RADIUS server, the AAA group and the AAA methods used for
802.1X and MAB. Accounting is required so PacketFence can track the location and
the session of each node:

  radius-server host 192.168.1.5 key useStrongerSecret
  !
  aaa group server radius PacketFence
     server 192.168.1.5
  !
  aaa authentication dot1x default group PacketFence
  aaa accounting dot1x default start-stop group PacketFence
  !
  dot1x system-auth-control

===== RADIUS Dynamic Authorization (CoA)

Enable RADIUS Dynamic Authorization so PacketFence can push role/VLAN/ACL
changes back to the switch. CoA and Disconnect requests are accepted from the
servers of the AAA group listed here (UDP port 3799 by default):

  dot1x dynamic-authorization
  aaa authorization dynamic dot1x additional-groups group PacketFence

In PacketFence, set the *Deauthentication Method* of the switch to `RADIUS`.
After an access re-evaluation, the `DM requests received` counter of the
PacketFence server increases and the endpoint gets a new dynamic ACL:

  show radius

===== Additional RADIUS attributes (optional)

The switch can send LLDP and DHCP information of the endpoint in the RADIUS
requests, which helps PacketFence to profile the device:

  dot1x
     radius av-pair lldp system-name
     radius av-pair lldp system-description
     radius av-pair dhcp hostname
     radius av-pair dhcp parameter-request-list
     radius av-pair dhcp vendor-class-id

The LLDP attributes are only sent when LLDP runs on the access port, which is
the EOS default (see the 'VoIP' section below to re-enable it).

===== 802.1X with MAC Authentication Bypass (MAB)

Apply the following configuration on each access port that should be
authenticated. 802.1X is attempted first; if the supplicant does not respond,
the switch falls back to MAC authentication (MAB). A device that does not speak
802.1X (printer, IoT, etc.) is therefore authenticated by MAB with the same
configuration:

  interface Ethernet1
     switchport mode access
     switchport access vlan 1
     dot1x pae authenticator
     dot1x port-control auto
     dot1x host-mode single-host
     dot1x mac based authentication
     dot1x mac based access-list

`dot1x mac based access-list` is required to apply the downloadable ACL
(NAS-Filter-Rule) returned by PacketFence to each host.

To support multiple devices behind the port (for example a PC behind an IP
phone), authenticate each host individually:

  dot1x host-mode multi-host authenticated

===== VoIP

Arista EOS uses LLDP-MED to advertise the voice VLAN to IP phones. LLDP is
enabled by default on EOS; if it was disabled, re-enable it globally and on
the access ports:

  lldp run
  !
  interface Ethernet1
     lldp transmit
     lldp receive

Make sure the port authenticates each host individually
(`dot1x host-mode multi-host authenticated`) and set the voice VLAN on the
port:

  interface Ethernet1
     switchport phone vlan 100

PacketFence will return the `Arista-AVPair = device-traffic-class=voice` VSA
for nodes identified as VoIP devices.

===== Uplink

The uplink towards the rest of the network must not authenticate clients:

  interface Ethernet48
     switchport mode trunk
     switchport trunk allowed vlan 1-5,100
     dot1x port-control force-authorized

===== Dynamic ACL (NAS-Filter-Rule)

The Arista module supports per-role ACLs pushed in the RADIUS Access-Accept
using the `NAS-Filter-Rule` attribute. To use it:

* In _Configuration -> Policies and Access Control -> Switches_, edit your
  Arista switch entry and enable *Role by access list*.
* Define the ACL for each role under _Configuration -> Policies and Access
  Control -> Roles_, for example for the registration role:

  permit tcp any host 192.168.1.5 eq 80
  permit tcp any host 192.168.1.5 eq 443
  permit udp any any eq 53
  permit udp any any eq 67
  permit udp any any eq 68
  deny ip any any

PacketFence translates each line and sends it as one `NAS-Filter-Rule`:

  NAS-Filter-Rule = "permit in 6 from any to 192.168.1.5 80"
  NAS-Filter-Rule = "permit in 6 from any to 192.168.1.5 443"
  NAS-Filter-Rule = "permit in 17 from any to any 53"
  NAS-Filter-Rule = "permit in 17 from any to any 67"
  NAS-Filter-Rule = "permit in 17 from any to any 68"
  NAS-Filter-Rule = "deny in ip from any to any"

The switch installs them as a dynamic ACL on the port:

  show ip access-lists dynamic

WARNING: The switch ends the per-host ACL with an implicit deny. An ACL made
only of `deny` lines blocks all the IPv4 traffic of the device, DHCP included,
so always permit at least DHCP and DNS (or end the ACL with `permit ip any any`
when the role must keep network access).

===== Web authentication (captive portal redirection)

EOS can hold a device authenticated by MAB (or 802.1X) in a captive portal
state and redirect its web requests to PacketFence, instead of moving it to the
registration VLAN. PacketFence returns the `Arista-WebAuth = start` and
`Arista-Captive-Portal = <url>` attributes, the switch answers the device's
HTTP (and HTTPS) requests with a redirection to that URL and, once the device
is registered, PacketFence disconnects the session so that it authenticates
again with its final role.

The pre-authentication ACL is what makes the switch intercept the web traffic:
its `deny ... copy captive-portal` entries send a copy of the matching packets
to the redirector. Define it on the switch, allowing DHCP, DNS and the
PacketFence portal:

  ip access-list PF-WEBAUTH
     10 permit udp any any eq bootps
     20 permit udp any any eq domain
     30 permit tcp any any eq domain
     40 permit ip any host 192.168.1.5
     50 deny tcp any any eq www copy captive-portal
     60 deny tcp any any eq https copy captive-portal
     70 deny ip any any

Then enable the captive portal under `dot1x`. The `url` is the fallback when
the RADIUS reply carries none, and the ACL is used when the reply does not name
one in `Filter-Id`:

  dot1x
     captive-portal url http://192.168.1.5 ssl profile PF-WEBAUTH
     captive-portal access-list ipv4 PF-WEBAUTH
     captive-portal start limit infinite

The `ssl profile` is only needed to intercept HTTPS requests (TCP port 443
only). Generate a key and a certificate on the switch, then reference them in
a profile:

  security pki key generate rsa 2048 webauth.key
  security pki certificate generate self-signed webauth.crt key webauth.key validity 3650 parameters common-name 192.168.1.16
  management security
     ssl profile PF-WEBAUTH
        certificate webauth.crt key webauth.key

In PacketFence, edit the switch and:

* enable *External Portal Enforcement*,
* in the *Roles* tab, enable *Role by Web Auth URL* and set the registration
  URL to `http://<your_captive_portal_ip>/Arista::AristaSwitch`,
* keep the registration VLAN set to the VLAN where the device gets an IP
  address while it is redirected (it is sent along with the captive portal
  attributes).

NOTE: EOS supports one device per port in the captive portal state (`dot1x
host-mode single-host`). A device without any pre-authentication ACL goes to
the `WEB-AUTH-FAILED` state.

===== Flow export (sFlow or IPFIX)

The switch can export sampled traffic to the Fingerbank collector of
PacketFence, either as sFlow (UDP 6343) or as IPFIX (UDP 4739). Use one or the
other: on the 720 series, sampled flow tracking only starts when sFlow is
stopped (`show agent SftAgent runnability` reports
`Not satisfied: Sflow agent is not running` otherwise).

sFlow:

  sflow sample 500
  sflow polling-interval 10
  sflow destination 192.168.1.5
  sflow source 192.168.1.2
  sflow run
  !
  interface Ethernet1
     sflow enable

Here 192.168.1.2 is the switch management IP.

IPFIX:

  no sflow run
  !
  flow tracking sampled
     sample 500
     tracker packetfence
        record export on inactive timeout 15000
        record export on interval 60000
        exporter packetfence
           collector 192.168.1.5 port 4739
           format ipfix version 10
           local interface Vlan1
           template interval 60000
     no shutdown
  !
  interface Ethernet1
     flow tracker sampled packetfence

The local interface is the interface that holds the switch management IP, it
is the source address of the export. Apply the tracker on every access port and
on the uplink. To check the exporter, `show flow tracking sampled` must report
`Running: yes`, and the counters of `show flow tracking sampled counters` must
increase.

===== Troubleshooting

`show dot1x hosts interface Ethernet1 detail` shows the authentication method,
the VLAN and the NAS-Filter-Rule returned by PacketFence for each host. With
web authentication, it also shows the captive portal URL and the
`WEB-AUTH-START` state; `show dot1x captive-portal counters` counts the web
requests redirected on each port. Counters staying at zero while the device
can't browse mean that the pre-authentication ACL lacks the
`copy captive-portal` entries.

`show radius` shows the messages sent and received for each RADIUS server.
Requests that time out without any message received mean that the RADIUS server
does not answer the switch: the switch is not declared in PacketFence or the
RADIUS secret differs.

PacketFence translates role ACLs written in the Cisco syntax
(`permit tcp any host 192.168.1.5 eq 443`) into `NAS-Filter-Rule` entries. A
line that can't be expressed as a rule is not sent, and a warning is logged in
[filename]`packetfence.log`:

* a source address other than `any` (the rule is always sent from any),
* a source port, a port operator other than `eq`, TCP flags (`established`, ...)
  and ICMP types,
* a protocol without a number (`nos`, an object group),
* a non contiguous destination mask, and `host 0.0.0.0` (0.0.0.0 is only sent as
  any),
* the `dscp`, `precedence`, `tos`, `fragments`, `time-range` and `option` qualifiers,

With _Push ACLs_ enabled on the switch, only source ports, ICMP types,
`host 0.0.0.0` and the qualifiers above are skipped.

Skipping a `permit` only narrows the role. Skipping a `deny` would let the lines
after it allow what it blocks, so the ACL is cut at that `deny` and ends with a
deny of all the traffic. A role whose lines were all skipped, or whose ACLs
PacketFence cannot parse, gets that deny all too: sending no ACL would leave the
endpoint unrestricted. Check [filename]`packetfence.log` for the warning naming
the line.

===== PacketFence switch configuration

In the PacketFence administration interface, add the switch under
_Configuration -> Policies and Access Control -> Switches_ using the following
parameters:

* Type: `Arista Switch`
* Mode: `production`
* Deauthentication Method: `RADIUS`
* RADIUS Secret: `useStrongerSecret`
